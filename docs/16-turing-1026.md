# 16. Turing-1026: a post-quantum key-encapsulation mechanism (step 12)

We wanted Turing's post-quantum part to be Turing's own, not an existing
scheme under a new name. Turing-1026 is a key-encapsulation mechanism (KEM):
a sender who knows a recipient's public key makes a random 256-bit key and a
ciphertext that only the recipient can open, and that key then keys Turing or
Turing-256. It is named after its lattice dimension, 1026.

```
cargo test --release -p turing turing1026       # the KEM's unit tests
cargo test --release -p bombe --test turing1026 # against the independent reference and the vectors
cargo run --release -p bombe -- attack          # section 25 attacks it
cargo run --release -p bombe -- vectors --turing-1026
cargo run --release -p bombe -- weak-keys       # per-key failure distribution
cargo run --release -p bombe -- fault-map       # decapsulation under transient faults
python tools/mutate.py --round7                 # 21 planted bugs
python research/scripts/pq/t1026_sweep.py       # the parameter search below
ACS_ESTIMATOR=<lattice-estimator> sage -python research/scripts/pq/t1026_real_sage.py
ACS_ESTIMATOR=<lattice-estimator> python research/scripts/pq/t1026_optimizer_audit.py matzov turing
```

## What is ours and what is not

docs/02 explains why Turing did not plan to invent its public-key part.
Rainbow and SIKE, both years into NIST's review, fell in 2022 to attacks on
the new algebraic structure they rested on. Turing-1026 keeps that lesson by
drawing the line somewhere else:

| Part | Turing-1026 | Where it comes from |
|---|---|---|
| Hard problem | Learning with errors (LWE), unstructured: no ring, no module, no rounding | Regev 2005; the problem FrodoKEM rests on, the most conservative lattice assumption |
| Encryption on it | Lindner-Peikert encryption with one message bit per coefficient | Lindner and Peikert, CT-RSA 2011; the textbook construction |
| Parameters | n = 1026, q = 2^15, CBD(18) noise, S 1026 x 32, S' 8 x 1026 | ours, chosen below with reproduced attack-cost and exact failure computations |
| Noise | centred binomial, the same law for secrets and errors, standard deviation 3 | the law is ML-KEM's; the width, 18 bits each way, is ours |
| Hashing | cSHAKE256 under eleven "Turing-1026 v1 ..." labels | ours, Turing's labelling rule (docs/03) |
| Transform | Fujisaki-Okamoto with implicit rejection, salted, the public key's hash in the coins and the rejection key, single-seed keys, a key check and a pair-wise check, default-fail selection | ours as a combination; each ingredient is published |
| Implementation | Rust, constant-time, secrets in memory locked where the OS allows it (reported), no residue | ours, checked by Bombe and the residue tests |

The lattice is the core of the design, not a wrapper around someone else's
KEM. `turing::lwe` generates A, samples the noise, computes B = A S + E,
encrypts (B' = S' A + E', C = S' B + E'' + Encode(mu)) and decrypts
(Decode(C - B' S)), all in this repository's code, and the workspace depends
on no post-quantum or KEM library (Cargo.lock: SHA-3, OS randomness, zeroize,
libc). The transform builds a KEM on that lattice encryption, and the KEM's
key is the Turing-256 key: `tests/turing1026.rs` encrypts with Turing-256
under an encapsulated key and decrypts with the key the recipient's lattice
decryption recovers. Bombe's lattice attack breaks exactly this code at
small dimension, so the lattice is what carries the security.

Nothing here is a new hardness assumption. What could be wrong is the
parameters, the transform or the code, and each has its own check below.
The research behind the choices is in `research/notes/pq/`.

## Specification

| | Value | |
|---|---|---|
| LWE dimension n | 1026 | A is 1026 x 1026 |
| Modulus q | 2^15 | reductions are masks; nothing divides |
| Noise | CBD(18): (sum of 18 bits) - (sum of 18 bits), variance 9 | for S, E, S', E', E'' alike |
| nbar, mbar | 32, 8 | S is n x 32; S' is 8 x n |
| Message | 8 x 32 = 256 coefficients, one bit each | 256-bit message mu |
| Public key | seed_a (32 bytes) and B packed, 15 bits per coefficient | 61,592 bytes |
| Ciphertext | B' (8 x 1026) and C (8 x 32) packed, then a 64-byte salt | 15,934 bytes |
| Secret key | one 32-byte seed | everything else is derived |
| Shared key | 32 bytes | a Turing or Turing-256 key |

Arithmetic is mod 2^15. Packing puts coefficient i at bits [15i, 15i + 15)
of a little-endian bit string, and every field is used, so any byte string
of the right length is a valid public key or ciphertext.

Key generation starts from the seed: (seed_a, r, z) = cSHAKE256(seed, "key
generation"), cut into 32-byte pieces. Row i of A is cSHAKE256(seed_a || i,
"matrix"), with i as 2 bytes little-endian and each coefficient 2 bytes
little-endian, taken mod q. S and then E, row by row, are drawn from
cSHAKE256(r, "key noise"). Each sample uses the next 36 bits, least
significant bit of each byte first: the first 18 count +1 and the next 18
count -1. B = A S + E, and the public key is seed_a || B. Last comes a
pair-wise check: encapsulate to the new key with a message and salt derived
from the seed ("key check"), decapsulate, and compare.

Encapsulation takes mu (32 bytes) and salt (64 bytes) from cSHAKE256 of a
64-byte OS seed ("encapsulation"). Then (r', k) = cSHAKE256(H(pk) || mu ||
salt, "coins"), 64 + 32 bytes, with H(pk) = cSHAKE256(pk, "public key"). S',
E' and E'' come from cSHAKE256(r', "encryption noise"). B' = S' A + E' and
C = S' B + E'' + Encode(mu), where Encode puts bit b at b q/2. The
ciphertext is c = B' || C || salt, and the shared key is
K = cSHAKE256(c || k, "shared key").

Decapsulation computes mu' = Decode(C - B' S), rounding each coefficient to
the nearer of 0 and q/2. It then recomputes (r', k') and re-encrypts mu'.
The output starts as the rejection key cSHAKE256(z || H(pk) || c, "rejection
key") and is replaced by cSHAKE256(c || k', "shared key") through a mask
that is all ones exactly when the re-encryption equals the received
ciphertext. Every step runs whatever the result, and only a wrong length is
an error. (The implementation decodes three times, in random orders drawn
under "decode order", and computes the rejection key twice, against faults;
the results are the ones specified here.)

All eleven labels begin "Turing-1026 v1 ": key generation, matrix, key
noise, key check, encapsulation, coins, public key, encryption noise,
shared key, rejection key and decode order. The code is `turing::lwe` (the
encryption, for any parameter set) and `turing::turing1026` (the KEM).

## Choosing the parameters

Two numbers have to be right: what the best lattice attack costs, and how
often decryption fails. We computed both with tools that first reproduce
published tables: the research's `coresvp.py` and `dfr.py`, and Bombe's own
ports of them (`coresvp`, `dfr`), which agree with the Python to every
printed digit.

Decryption fails when a coefficient of S'E - E'S + E'' leaves [-q/4, q/4).
That error is a sum of 2n = 2052 products of two noise samples, with
standard deviation about sqrt(2n) sigma^2 = 408 here. Wider noise makes the
lattice harder and failures likelier, and at n near 1000 both depend almost
only on sigma^2 / q (the research's finding 10 in
attack-cost-estimation.md). The sweep confirms it:

| q | CBD | sigma | sigma^2 / q | failure rate | classical core-SVP (primal / dual) |
|---|---|---|---|---|---|
| 2^15 | 14 | 2.65 | 2.14e-4 | 2^-425.5 | 246.0 / 244.8 |
| 2^15 | 16 | 2.83 | 2.44e-4 | 2^-332.2 | 250.1 / 248.9 |
| **2^15** | **18** | **3.00** | **2.75e-4** | **2^-266.1** | **253.9 / 252.4** |
| 2^15 | 20 | 3.16 | 3.05e-4 | 2^-217.5 | 257.1 / 255.9 |
| 2^16 | 36 | 4.24 | 2.75e-4 | 2^-265.5 | 253.3 / 252.1 |
| 2^14 | 10 | 2.24 | 3.05e-4 | 2^-218.2 | 257.4 / 256.2 |

The table is for n = 1026, 256 coefficients and samples m = n + 32;
`t1026_sweep.py` prints the full version. The rule the research gives for
the failure rate is at most 2^-lambda for lambda bits of security, computed
exactly and met by a proven bound (decryption-failures.md, finding 10).
FrodoKEM and HQC follow it, NIST IR 8545 states it, and ML-KEM-1024 misses
it by 81 bits. CBD(18) at q = 2^15 is the widest noise that meets it:
2^-266.1 against the weakest attack's 2^-252.4. CBD(20) would give 2^-217.5
against 2^-255.9.

The other choices around it, and why:

- We use one bit per coefficient. Two bits per coefficient would halve the
  window, and keeping the failure rate would then need half the noise
  variance (CBD(9)): 233.4 / 232.3 instead of 253.9 / 252.4, 20 bits less.
  256 one-bit coefficients keep the window at q/4.
- We picked q = 2^15 rather than 2^16 or 2^14. Equal sigma^2 / q gives equal
  security and failures, so q is a free choice: 2^15 packs in 15 bits, and
  its sigma = 3 keeps the secret wide. The research found that the
  dual-hybrid attack, which guesses secret coordinates, beats the primal
  attack by 6-14 bits when the secret's standard deviation is 1.4 or less,
  and loses to it at 2.3-2.8 (attack-cost-estimation.md, item 2a).
  q = 2^14 would need sigma = 2.1.
- We set nbar = 32 and mbar = 8. The message needs 32 x 8 coefficients
  either way. The public key grows with nbar and the ciphertext with mbar,
  and a recipient's key is published once while every wrapped file carries a
  ciphertext, so we made the ciphertext the small side (15.9 KB, the size of
  FrodoKEM-976's). Encapsulation and decapsulation then do a quarter of key
  generation's matrix work.
- The noise is centred binomial. It is exact, sampled with population
  counts in constant time, and its law is known in closed form, so the
  failure computation needs no table. Its width is what the table above
  chose.
- We use no error-correcting code and no ciphertext compression. Both lower
  the failure rate or the size on paper, and both have broken schemes (LAC's
  failures were 2^48 times likelier than its estimate; compression is the
  one heuristic in ML-KEM's failure analysis). Without them the failure law
  above is exact, not heuristic.

For security we use classical and quantum core-SVP (sieving at 2^0.292b and
2^0.265b per BKZ-b call, every polynomial factor left out, which favours the
attacker), and the lattice-estimator (commit 53da598, all its attacks, run
both under the research's SageMath stand-in and under real SageMath 10.7,
each reproducing the estimator's own published outputs first):

| | Turing-1026 | ML-KEM-1024 | FrodoKEM-976 | FrodoKEM-1344 |
|---|---|---|---|---|
| Classical core-SVP, primal / dual (one convention) | 253.9 / **252.4** | 255.3 / 253.9 | 206.5 / 205.6 | 271.7 / 270.5 |
| Quantum core-SVP | 228.9 | 230.2 | 186.5 | 245.4 |
| Lattice-estimator, cheapest attack (default model) | **269.7** (primal BDD) | 262.3 (dual-hybrid) | 225.2 (primal BDD) | 281.7 (dual-hybrid) |
| Lattice-estimator, cheaper of primal and dual-hybrid in its core-SVP model | 253.7 | 241.8 | 206.4 | 261.0 |
| Decryption failure | **2^-266.1** | 2^-174.8 | 2^-199.6 | 2^-252.5 |
| Public key / ciphertext (bytes) | 61,592 / 15,934 | 1,568 / 1,568 | 15,632 / 15,744 | 21,520 / 21,632 |

The core-SVP rows use one convention for all four: the GSA model of ADPS16
as NewHope's scripts run it. FrodoKEM's own tables add log2 b, which puts
Turing-1026 at 261.6 and FrodoKEM-1344 at 279.8. Of Turing-1026's two LWE
instances, the ciphertext's (n + 32 samples per row of S') is the weaker;
the key's gives 254.2 / 253.0. The estimator treats ML-KEM-1024 as plain
LWE, as every published estimate does.

On the plain core-SVP count Turing-1026 is at ML-KEM-1024's level. It is
ahead of it once hybrid attacks are counted (ML-KEM's narrow secret loses 8
to 13 bits to the dual-hybrid, depending on the cost model), behind
FrodoKEM-1344, and has the lowest failure rate of the four. The cost is
size: its public key is 39 times ML-KEM-1024's.

We did not take the 269.7 figure on trust. We checked the estimator three
ways:

1. We ran it under real SageMath, not only the research's numeric
   stand-in. Under SageMath 10.7 the estimator (commit 53da598) reproduces
   all ten of its own published outputs (Kyber512/768/1024, LightSaber;
   primal, dual, hybrid and rough variants) to 0.05 bit with matching block
   sizes, then gives Turing-1026 the same numbers the stand-in did: primal
   BDD 2^269.7 (beta 850) in the default model, uSVP 2^253.7 in the
   core-SVP model, identical to the table. Arora-Ge returns infinity (the
   noise is far too wide for it), as it should. `t1026_real_sage.py` runs
   it.
2. We tested the estimator's greedy ζ/t search (issue #219). Its MATZOV
   dual-hybrid steps its guessing dimension ζ and FFT dimension t by 10 and
   stops at the first cost rise (`util.early_abort_range`), and issue #219
   reports that this misses the optimum by about 1 bit on ML-KEM.
   `t1026_optimizer_audit.py` swaps in an exhaustive search (every ζ, t, and
   a full β scan at each point). On ML-KEM-1024 it reproduces the flaw:
   2^261.1 against the estimator's 2^262.3, ζ near 32 not 0. On Turing-1026
   the flaw is much larger: the estimator's dual-hybrid stops at t = 0 and
   reports 2^278.2, while the true optimum is at t = 55, ζ = 20, 2^269.5
   (−8.75 bits). That only brings the dual-hybrid down to the primal BDD's
   level, though. The cheapest attack was already primal BDD at 2^269.7, so
   the audited figure is 2^269.5, essentially unchanged. (The gap over
   ML-KEM-1024, whose audited cheapest is 2^261.1, if anything widens.) The
   dual-hybrid's guess uses m = n samples throughout, as the estimator does.
3. We tried a wider primal β range for the estimator (issue #149). Its
   primal_bdd and primal_hybrid search β only up to the uSVP optimum + 1,
   and issue #149 proposes widening it. Widening it to uSVP ± 80 and
   re-optimising the dimension d leaves Turing-1026's primal BDD at 2^269.74,
   beta 850, unchanged: the estimator had already found its optimum.

The audit moves Turing-1026's cheapest default-model attack from 2^269.7 to
2^269.5, and confirms the core-SVP figures under real SageMath. The
research's remaining caution still applies: core-SVP moves by a bit between
published scripts, and no confirmed polynomial-time quantum attack on LWE
exists as of 2026-09-27 (attack-cost-estimation.md, section 8).

We build the failure law by convolution (2052 products of CBD(18) samples
plus one more). The union bound over the 256 coefficients needs no
independence between them, and gives 2^-274.06 per coefficient and 2^-266.06
per ciphertext. Bombe's `dfr` first reproduces FrodoKEM's published rates
(2^-138.7, 2^-199.6, 2^-252.5) to 0.05 bit, and matches `dfr.py` on
Turing-1026 to 0.05 bit. The real code agrees with the law. At two small
parameter sets where failures are common, 3.2 million decrypted bits each,
it fails 2.056e-4 of the time against the law's 2.078e-4 (z = -0.25), and
1.2453e-2 against 1.2480e-2 (z = -0.33).

The figure 2^-266.06 is an average over key generation, which is exactly
what the Fujisaki-Okamoto delta-correctness bound uses. A key is used many
times, though, so an unlucky key's own rate matters. For a fixed key the
error of coefficient (i, j) is X = Σ_k E[k][j] S'[i][k] - S[k][j] E'[i][k] +
E''[i][j]: the key's column entries times fresh CBD(18) samples. Only the
histogram of |S| and |E| in that column decides its law. `bombe weak-keys`
bounds it in two ways, both proven, and then measures it:

- Markov gives the first bound. A key's failure bound (the union over its
  256 coefficients) averages to 2^-266.06, so at most 2^-x of keys have a
  bound above 2^-y for x = 266.06 - y. At most 2^-13.6 of keys exceed
  2^-252.4.
- The column norms give the second, through Chernoff and Jensen. CBD(18) has
  moment generating function cosh(t/2)^36, which gives a proven Chernoff
  bound per column. Since ln cosh(√u) is concave, Jensen says a column's
  bound is at most that of one whose entries all share its squared norm N, a
  function of N alone, and the exact law of N is a convolution. A union
  bound over the 32 columns gives at most 2^-7.7 of keys above 2^-252.4.
  The two bounds cross around there: the norm bound wins further out (2^-95
  above 2^-200), Markov nearer the mean.
- Then we measured it on 100,000 keys, drawn exactly as key generation
  draws S and E, with each column's rate from a Lugannani-Rice saddlepoint
  approximation (checked against the exact convolution to under 0.001 bit on
  the heaviest keys). The worst key was 2^-253.2, one in 10,000 was above
  2^-256.1, and the median was 2^-275.8. None of the 100,000 exceeded the
  2^-252.4 security level, and the five heaviest, recomputed by exact
  convolution, land at 2^-253.2 to 2^-255.3.

What is proven, then, is that at most a 2^-13.6 fraction of keys could have
a failure rate worse than the weakest lattice attack, and no key was
observed anywhere near it. The delta the transform uses is the average, and
it holds. CBD(18) is right at the edge here (a wider noise would widen
this tail), which is one more reason the parameter table above stops at 18.

## The transform

Lattice encryption alone is secure only against passive attackers: with a
decryption oracle, a reused key falls in about 1,200-2,200 queries at
Kyber's sizes (cca-transforms-and-binding.md, finding 1). The
Fujisaki-Okamoto transform makes it secure against chosen ciphertexts by
deriving the encryption's coins from the message and re-encrypting on
decapsulation. Here is Turing-1026's version, ingredient by ingredient:

| Ingredient | What it buys | Source |
|---|---|---|
| FO with implicit rejection (HHK17's U-not-bot) | IND-CCA from IND-CPA and a failure rate delta, in the random-oracle model and (with a square-root loss) the quantum one | Hofheinz, Hövelmanns, Kiltz 2017 |
| A 64-byte salt in the coins and, through c, in both keys | multi-target security: many ciphertexts under one key no longer help a collision search; the salt must enter both keys, or binding breaks as it did for round-4 HQC | salted FrodoKEM; Glabush, Hövelmanns, Stebila (IACR CiC 2026) |
| H(pk) in the coins and in the rejection key | the accepted key depends on the recipient's key, and the rejection key cSHAKE256(z, H(pk), c) gives every MAL binding notion | FO_M, Krämer, Struck, Weishäupl 2025 |
| One 32-byte seed as the secret key | z is derived with everything else, which MAL-BIND-K-PK needs; the decapsulator never accepts an expanded key | Schmieg 2024 |
| Distinct cSHAKE256 labels for G, H, the key and the rejection key | independent random oracles, the oracle cloning the proofs assume | Bellare, Davis, Günther 2020 |
| Failure rate 2^-266 | the delta term of every bound is negligible; no failure-boosting attack reaches it under a 2^64-query limit | decryption-failures.md, section 4 |
| Pair-wise check at key generation | a key corrupted while being made (Rowhammer did this to FrodoKEM) fails at once | FIPS 203 section 7.1 |
| Default-fail selection | the output is the rejection key unless the mask replaces it, so a skipped instruction rejects | pqm4 fault attacks (side-channels note, finding 9) |

No single paper proves this exact combination (salted FO with FO_M
rejection; the research's open question 4). Each piece is proven, the salt
is known not to disturb the binding results, and FO_M changes only a public
input to the rejection hash, so the combination is argued, not proven.
docs/17 writes the scheme down exactly, states the IND-CCA claim and game,
and goes through every departure from the salted-FrodoKEM transform the
theorems cover, checking that each keeps their hypotheses.
Rejection will be explicit at the file level anyway (a wrong key fails the
file's authentication), which Hövelmanns and Kudinov show is as secure as
implicit rejection in the random-oracle model, up to a rare edge case
(PQCrypto 2025).

## Implementation

- For constant time, secret values are only added, multiplied, masked and
  shifted. `tools/asm_branches.py` now has a `--divs` mode (the KyberSlash
  class), and the release build of `lwe` and `turing1026` holds no division
  except three that divide constant allocation sizes by the page size. A
  first version had divisions of public slice lengths from `chunks_exact`;
  the loops now slice by multiplication, so the scan reads zero there. Every
  conditional jump in decryption, sampling, packing and decapsulation tests
  a length, a loop counter, a bounds check or the XOF's position, never a
  decoded bit, a noise value or the comparison.

  We ran dudect twice through full campaigns (a leak is |t| > 4.5).
  Decapsulation of valid against tampered ciphertexts gave |t| 1.3 and 2.2
  over 3,000 runs. The re-encryption comparison alone, equal against
  differing, gave 1.2 and 0.9 over 200,000. Key generation from fixed
  against random seeds gave 1.7 and 3.2 over 600. An early-exit comparison
  put through the same test as the re-encryption check is caught at |t| 358
  and 416.
- The expanded secret (seed, S, z) and each operation's scratch (message,
  coins, S', the re-encryption) live in their own allocations, locked where
  the operating system allows it and wiped on drop. Locking is limited
  (Windows: about the minimum working set; Linux: RLIMIT_MEMLOCK). When a
  lock is refused for that reason the allocation raises the limit and tries
  once more, and `memory::unlocked_allocations()` counts any secret that
  still ended up unlocked. The review of 2026-09-28 (R11) found that under
  Windows' default limits the third key and every workspace after two keys
  were unlocked, unreported.

  Secret hashing uses `xof::SecretXof`, cSHAKE256 written on Keccak-f
  directly. Its state is never on the stack: it lives in its own allocation,
  is wiped in place (`wipe`), and every public operation runs its work in an
  `#[inline(never)]` frame below a stack burn. A leftover sponge state gives
  its input back through one inverse permutation. Before the review of
  2026-09-28 (R1), `drop(x)` wiped a moved copy of the key check's state,
  the original stayed in `from_seed`'s own frame above the burn, and the
  seed, the whole private key, was recovered from it blind in 10 of 10 key
  generations. A residue test now records every secret sponge's final state
  and searches dead stack for it after key generation, encapsulation and
  decapsulation (it fails on the unfixed code). Bombe's memory scan finds
  the seed, the noise seed, z, the message, the coins, k and the keys only
  where they belong, after key generation, after an encapsulation and two
  decapsulations, and after drop. S itself is not searched for: an 8-byte
  fragment of it holds about 14 bits, too few to tell a copy from chance.
  Key generation, encapsulation and decapsulation use at most 3.6, 3.8 and
  4.5 KB of stack, within the 32 KB burn.
- Key generation has two fault checks, each computed whatever the other
  says. The key check (`lwe::check_key`) recomputes A S and requires every
  entry of B - A S to lie in [-18, 18]. A change of any S entry by d moves
  its column of A S by A[i][k] d in all 1026 rows, so every single-bit flip
  in bits 0-14 of S between expansion and the checks is caught,
  deterministically (exhaustively on a small parameter set, and on 240
  random flips here). Bit 15 changes an entry by 2^15, which is 0 mod q, so
  it changes nothing. The pair-wise check (encapsulate to the new key with a
  message and salt derived from the seed, decapsulate, compare) runs the
  whole pipeline. On its own it misses about 2^-8 of the flips, since one
  ciphertext's 8 rows each notice a flip with probability about 1/2. The
  review of 2026-09-28 (R5) measured this: 10 of 3,000 random flips slipped
  through, and every key that slipped through kept the published public key
  and decapsulated 99 of 100 honest ciphertexts wrongly. That is the setting
  of Fahr et al., "When Frodo Flips", CCS 2022, whose section 8.2 recommends
  recomputing B.
- The re-encryption check is where a glitch does the most damage in
  decapsulation: forcing it to accept makes the KEM the bare lattice
  decryption oracle again, which is what the transform removes (the pqm4
  attacks). So the re-encryption is computed twice, independently, into the
  same buffers, and compared to the received ciphertext three ways: the
  first run as packed bytes (`eq_mask`), the second as coefficients B', C
  (`eq_mask_u16`) and, packed again, as bytes. Two chained constant-time
  selections install the accepted key only if the first two verdicts both
  accept, the output starting as the rejection key. The third verdict binds
  the accepted key itself to the comparison: the key is
  cSHAKE256(c || k' xor K-bar) unless the third verdict accepts, and K-bar
  needs z. Two runs are needed because a first design packed a single
  re-encryption and compared it both ways. Both comparisons then read the
  same coefficients, so one fault on them before packing fooled both (an
  independent review found this).

  `bombe
  fault-map` injects every fault of the model into the real decapsulation
  code and classifies each against the independent reference. The model
  covers the decoded message, the coins, each re-encryption's coefficients
  before it is read, each verdict, the rejection and accepted keys, and the
  selection, and the hooks that inject them compile to nothing in the
  production build. No single fault bypasses the check: forcing one
  verdict, or one re-encryption's coefficients, is caught, and skipping the
  selection leaves the rejection key. Forcing both selection verdicts
  releases a key bound to the comparison, useless without z. The cheapest
  bypasses take two correlated faults, both on the second run's side or both
  runs' data (the second run's coefficients and the byte verdict, or both
  runs' coefficients), or three verdicts.

  The fault map runs a separate compilation of this code (with its hooks),
  so the production machine code is checked on its own. Until the review of
  2026-09-28 (R2) the release build had fused the two selections, which
  compute `out ^= (out ^ k) & (a & b)`, into one mask (one `sar`, one
  select), a single-fault bypass the fault map could not see. The selections
  are now separate non-inlined functions with their masks behind value
  barriers, and `tools/ct_check.py` fails unless the release build derives
  three masks separately and calls `select_into` twice and
  `bind_to_verdict` once (on the unfixed build it reports all three failed).
  Two single faults that redundancy in the comparison cannot reach used to
  leak, and each is now closed by redundancy of its own.

  The first is the rejection key. An XOF-state fault that skips absorbing z
  made the returned key computable from public values, which is a validity
  oracle. The rejection key is now computed twice, independently, and if the
  two disagree the result is K-bar xor a fresh unpredictable value
  (`infect`), so a skip in either computation gives the attacker a key it
  cannot predict. The fault map's control (one computation, as before) still
  shows the oracle; the real code needs two faults (z skipped in both, or
  one skip and the agreement verdict forced).

  The second is the decoder. Skipping the `+ q/4` of one coefficient's
  rounding made a valid ciphertext decode correctly exactly when that
  coefficient's noise is non-negative. So whether decapsulation gave the
  real key or the rejection key told the attacker the sign of a known linear
  function of (S, E). This is Pessl and Prokop's effective/ineffective fault
  attack (TCHES 2021(2), abstract and section 7.1). It only has to tell an
  effective fault from an ineffective one, so "various detection-based
  countermeasures, including many forms of double execution, can be
  bypassed": a detected fault is as visible as a wrong result. Correcting
  the fault does stop it. Decryption now runs three times, each pass
  computing C - B'S afresh and decoding in its own random order (a
  Fisher-Yates permutation drawn, without a secret-dependent branch or memory
  access, from cSHAKE256 of z, a count of the key's decapsulations and 32
  bytes from the operating system), and each message bit is the majority of
  the three. One skipped rounding, or one fault in a pass's arithmetic
  (C - B'S shifted at one coefficient), at any step or coefficient of any
  pass, is outvoted: the fault map tries all 768 of each and none changes a
  valid ciphertext's result, while its control (one pass, in order, as
  before) leaks exactly the coefficients whose noise is negative (128 of 256
  for its key). Each layer also holds alone. With the vote skipped (one more
  fault), the random order still hides which coefficient a skipped rounding
  hit, and the outcomes follow the noise signs by index at chance level (128
  of 256, against 256 of 256 in order). Shuffling and fine-grained
  redundancy are among the answers the literature gives
  (research/notes/pq/side-channels-faults-and-ct-verification.md, finding 9
  and section 4.2). The vote is the redundancy we chose, since it corrects a
  fault where double execution only detects one.

  Two faults are the decoder's boundary, as they are the check's. Skipped
  roundings in two passes meet on one coefficient only by chance (1 in 256,
  and the attacker does not learn which). But C - B'S is computed in a fixed
  order, so two faults aimed at one coefficient's arithmetic in two passes
  outvote the third and leak its noise sign. The fault map measures this
  (exactly the 128 negative-noise coefficients), and its test fails if that
  ever changes unnoticed. Randomising that order as well would not raise the
  bar, because two correlated faults on the re-encryptions' data already
  bypass the check.

  `tools/ct_check.py` checks that the release build keeps all of it: two
  rejection-key computations and the infection, three decryption passes,
  each with its own order and its own C - B'S, and the vote. The fault map,
  the order tests or `ct_check.py` catch each of these planted bugs:
  collapsing to one re-encryption, removing a comparison, the binding, the
  second rejection key, the infection, a decryption pass or the shuffle, or
  collapsing the chained selection (`mutate.py --round7`, `--review2`,
  `--review3`). The second re-encryption is why decapsulation costs about
  twice encapsulation; the three decryptions and the second rejection key
  add about 4%.
- `turing::self_test()` now also checks vector 2 of
  `vectors/turing-1026-v1.txt` (public key and ciphertext digests, shared
  key, and the rejection key of a tampered ciphertext), and ML-KEM-1024
  against a vector from the independent Python reference. It takes about
  45 ms here (release build, 2026-09-28).
- Speed here (one core, release build of the library alone, medians of
  2026-09-28): key generation takes about 38 ms with its two checks (29 ms
  with the pair-wise check alone), encapsulation about 6.5 ms and
  decapsulation about 13.4 ms (two re-encryptions and three decryptions for
  the fault checks above). Most of the time goes to expanding A from
  cSHAKE256.

## What was run

The checks are section 25 of `bombe attack`, and `tests/turing1026.rs`:

- The implementation matches an independent reference (`refkem1026`: the
  sha3 library's cSHAKE, A as a full matrix, i64 arithmetic, bit-by-bit noise
  and packing, decoding phrased as a range test) on public keys,
  ciphertexts, shared keys and rejection keys, and its LWE core matches at
  four small parameter sets, including ones where a sample's bits end
  mid-byte. It reproduces the four known-answer vectors, which the reference
  generated. A third implementation, in Python
  (`research/scripts/pq/turing1026_py.py`), reproduces the same four
  vectors. It uses pycryptodome's cSHAKE256 (a third Keccak) and NumPy for
  the matrix products, and was written from this document's specification,
  so a spec misreading shared by the two Rust implementations would show up
  as a mismatch.
- For attack cost, Bombe's core-SVP port reproduces 7 published rows
  (FrodoKEM round 3, NewHope round 2, ADPS16) with their block sizes, and
  perturbed parameters fail the match; then come Turing-1026's numbers
  above. The lattice-estimator itself was run under real SageMath 10.7 (all
  ten published outputs reproduced), with its greedy MATZOV search replaced
  by an exhaustive one (issue #219: −8.75 bits on Turing's dual-hybrid,
  which only reaches the primal BDD it already sat behind) and its primal β
  range widened (issue #149: no change). All of it is above.
- For failures we reproduced FrodoKEM's published rates, computed
  Turing-1026's exact rate and compared the real code's failure counts with
  the law. The per-key distribution (`bombe weak-keys`) gives the proven
  Markov and column-norm tail bounds and a measurement on 100,000 keys, with
  the five heaviest recomputed by exact convolution.
- The fault map (`bombe fault-map`) runs every fault of the model on a valid
  and an invalid ciphertext, and no single fault bypasses the two-comparison
  re-encryption check.
- The attack itself runs at small n. Bombe's LLL and BKZ run the primal
  attack the estimate prices on keys made by the real key generation, with
  Turing-1026's own q = 2^15 and CBD(18), n cut down:

  | n (lattice dimension 2n + 1) | 20-70 | 80 | 90 | 100 | 1026 |
  |---|---|---|---|---|---|
  | secret recovered by | LLL | BKZ-10 | BKZ-10 or BKZ-16 (one key each) | BKZ-20 (87 s) | BKZ-868 by the estimate |

  The estimate's success condition, fed the root Hermite factors this BKZ
  reaches on random lattices of the same shape (1.0179-1.0182 for BKZ-10,
  1.0167 for BKZ-16, 1.0158 for BKZ-20 at dimension 161), puts the largest
  n each breaks at 89-91, 96 and 100-101. So BKZ-10 breaks 80, sits at its
  limit at 90 (one key fell to it, another needed BKZ-16), and BKZ-16 fails
  at 100, where BKZ-20 succeeds. (LLL does worse than the condition predicts
  for it, n = 88; it already fails at 80. The condition is written for BKZ.)
  The campaign checks every observed break against the condition within 5
  dimensions. So the attack works on the real code, and grows with n as the
  model that prices n = 1026 says.
- For chosen ciphertexts, single-bit changes anywhere in a ciphertext, salt
  included, give the rejection key (the reference's, where compared). The
  right ciphertext under another key gives that key's rejection key, and
  wrong lengths are refused. `tests/turing1026_adversarial.rs` goes further,
  against the implementation and the reference together. It places C - B'S
  on each side of every decoding boundary and tries extreme and degenerate
  ciphertexts (all zero, all ones, a single nonzero coefficient), structured
  edits of a valid ciphertext (q/2 on one coefficient flips one message bit;
  small changes keep the message but still reject; salts swapped; halves
  spliced), and the key-mismatch attack. That attack recovers S from the
  bare lattice decryption in about six queries per entry, but through the
  KEM it gets only the reference's rejection key and learns nothing.
- Timing, memory, faults and stack are covered above.

## Planted bugs

`tools/mutate.py --round7` plants 21 bugs: rejection returning the decrypted
key, each of the two re-encryption checks always accepting, the chained
selection collapsed to a single check (the three caught by the fault map),
a rejection key without z or without H(pk), coins without the salt or without
H(pk), a shared key that ignores the ciphertext, a pair-wise check that always
passes, a message left unwiped, a noise sampler that skips a bit, decoding
that rounds down, packing that drops a bit, matrix rows that ignore their
index, cSHAKE padded like SHAKE, a failure law with n products instead of
2n, Chen's formula with the wrong exponent, LLL without size reduction,
enumeration trying one sign everywhere, and the reference's decoding window
shifted.

## What is not done

- Everything rests on one family of assumptions. A break of LWE breaks
  Turing-1026. The research's advice for guarding against that is a second,
  non-lattice KEM combined with it (hybrid-combiners.md), and X-Wing did that
  with X25519. Turing-1026 has no such partner yet.
- A proof of the transform for this exact combination (above).
- The file format (step 9). Turing-1026 makes the key; the AEAD that uses it
  and the header that carries the ciphertext are still to come.
- Masking. Nothing protects decapsulation against power analysis, and
  single-trace attacks on lattice code are known (side-channels note,
  finding 7). The same gap leaves the one fault the double check cannot
  close (skipping z in the rejection hash, above); both want the rejection
  and coin hashes computed redundantly or in masked shares.
- Multi-ciphertext security of LWE itself is unsettled in the literature
  (cca-transforms-and-binding.md, finding 6); a stated limit on ciphertexts
  per key belongs in the file format.
- Speed and size. Plain LWE is slow and large next to ML-KEM, the price of
  having no ring structure.
