# 16 — Turing-1026: a post-quantum key-encapsulation mechanism (step 12)

The owner asked for Turing's post-quantum part to be Turing's own, not an
existing scheme under a new name. Turing-1026 is a key-encapsulation
mechanism (KEM): a sender who knows a recipient's public key makes a random
256-bit key and a ciphertext that only the recipient can open, and that
key then keys Turing or Turing-256. It is named after its lattice
dimension, 1026.

```
cargo test --release -p turing turing1026       # the KEM's unit tests
cargo test --release -p bombe --test turing1026 # against the independent reference and the vectors
cargo run --release -p bombe -- attack          # section 25 attacks it
cargo run --release -p bombe -- vectors --turing-1026
python tools/mutate.py --round7                 # 20 planted bugs
python research/scripts/pq/t1026_sweep.py       # the parameter search below
```

## What is ours and what is not

docs/02 explains why Turing did not plan to invent its public-key part:
Rainbow and SIKE, both years into NIST's review, fell in 2022 to attacks on
the new algebraic structure they rested on. Turing-1026 keeps that lesson
by drawing the line in a different place:

| Part | Turing-1026 | Where it comes from |
|---|---|---|
| Hard problem | Learning with errors (LWE), unstructured: no ring, no module, no rounding | Regev 2005; the problem FrodoKEM rests on, the most conservative lattice assumption |
| Encryption on it | Lindner-Peikert encryption with one message bit per coefficient | Lindner and Peikert, CT-RSA 2011; the textbook construction |
| Parameters | n = 1026, q = 2^15, CBD(18) noise, S 1026 x 32, S' 8 x 1026 | **ours**, chosen below with reproduced attack-cost and exact failure computations |
| Noise | centred binomial, the same law for secrets and errors, standard deviation 3 | the law is ML-KEM's; the width, 18 bits each way, is ours |
| Hashing | cSHAKE256 under nine "Turing-1026 v1 ..." labels | **ours**, Turing's labelling rule (docs/03) |
| Transform | Fujisaki-Okamoto with implicit rejection, salted, the public key's hash in the coins and the rejection key, single-seed keys, a pair-wise check, default-fail selection | **ours** as a combination; each ingredient is published |
| Implementation | Rust, constant-time, secrets in locked memory, no residue | **ours**, checked by Bombe |

Nothing here is a new hardness assumption. What could be wrong is the
parameters, the transform or the code, and each has its own check below.
The research behind the choices is in `research/notes/pq/`.

## Specification

| | Value | |
|---|---|---|
| LWE dimension n | 1026 | A is 1026 x 1026 |
| Modulus q | 2^15 | reductions are masks; nothing divides |
| Noise | CBD(18): (sum of 18 bits) - (sum of 18 bits), variance 9 | for S, E, S', E', E'' alike |
| nbar, mbar | 32, 8 | S is n x 32; S' is 8 x n |
| Message | 8 x 32 = 256 coefficients, one bit each | 256-bit message mu |
| Public key | seed_a (32 bytes) and B packed, 15 bits per coefficient | 61,592 bytes |
| Ciphertext | B' (8 x 1026) and C (8 x 32) packed, then a 64-byte salt | 15,934 bytes |
| Secret key | one 32-byte seed | everything else is derived |
| Shared key | 32 bytes | a Turing or Turing-256 key |

Arithmetic is mod 2^15; packing puts coefficient i at bits [15i, 15i + 15)
of a little-endian bit string, and every field is used, so any byte string
of the right length is a valid public key or ciphertext.

**Key generation** from the seed: (seed_a, r, z) = cSHAKE256(seed, "key
generation") in 32-byte pieces. Row i of A is cSHAKE256(seed_a || i,
"matrix"), i as 2 bytes little-endian, 2 bytes per coefficient
(little-endian) mod q. S and then E, row by row, are drawn from
cSHAKE256(r, "key noise"), each sample from the next 36 bits, least
significant bit of each byte first (the first 18 count +1, the next 18 -1).
B = A S + E. Public key: seed_a || B. Then a
pair-wise check: encapsulate to the new key with a message and salt derived
from the seed ("key check"), decapsulate, compare.

**Encapsulation**: mu (32 bytes) and salt (64 bytes) from cSHAKE256 of a
64-byte OS seed ("encapsulation"). (r', k) = cSHAKE256(H(pk) || mu || salt,
"coins"), 64 + 32 bytes, with H(pk) = cSHAKE256(pk, "public key"). S', E',
E'' from cSHAKE256(r', "encryption noise"). B' = S' A + E', C = S' B + E'' +
Encode(mu), Encode putting bit b at b q/2. Ciphertext c = B' || C || salt.
Shared key K = cSHAKE256(c || k, "shared key").

**Decapsulation**: mu' = Decode(C - B' S), each coefficient rounded to the
nearer of 0 and q/2. Recompute (r', k') and re-encrypt mu'. The output
starts as the rejection key cSHAKE256(z || H(pk) || c, "rejection key") and
is replaced by cSHAKE256(c || k', "shared key") through a mask that is all
ones exactly when the re-encryption equals the received ciphertext. Every
step runs whatever the result. Only a wrong length is an error.

All nine labels begin "Turing-1026 v1 ". The code is `turing::lwe` (the
encryption, for any parameter set) and `turing::turing1026` (the KEM).

## Choosing the parameters

Two numbers have to be right: what the best lattice attack costs, and how
often decryption fails. Both were computed with tools that first reproduce
published tables: the research's `coresvp.py` and `dfr.py`, and Bombe's own
ports of them (`coresvp`, `dfr`), which agree with the Python to every
printed digit.

**The trade-off.** Decryption fails when a coefficient of S'E - E'S + E''
leaves [-q/4, q/4). That error is a sum of 2n = 2052 products of two noise
samples, standard deviation about sqrt(2n) sigma^2 = 408 here. Wider noise
makes the lattice harder and failures likelier. At n near 1000 both depend
almost only on sigma^2 / q (the research's finding 10 in
attack-cost-estimation.md), which the sweep confirms:

| q | CBD | sigma | sigma^2 / q | failure rate | classical core-SVP (primal / dual) |
|---|---|---|---|---|---|
| 2^15 | 14 | 2.65 | 2.14e-4 | 2^-425.5 | 246.0 / 244.8 |
| 2^15 | 16 | 2.83 | 2.44e-4 | 2^-332.2 | 250.1 / 248.9 |
| **2^15** | **18** | **3.00** | **2.75e-4** | **2^-266.1** | **253.9 / 252.4** |
| 2^15 | 20 | 3.16 | 3.05e-4 | 2^-217.5 | 257.1 / 255.9 |
| 2^16 | 36 | 4.24 | 2.75e-4 | 2^-265.5 | 253.3 / 252.1 |
| 2^14 | 10 | 2.24 | 3.05e-4 | 2^-218.2 | 257.4 / 256.2 |

(n = 1026, 256 coefficients, samples m = n + 32; `t1026_sweep.py` prints
the full table.) The rule the research gives for the failure rate is at most
2^-lambda for lambda bits of security, computed exactly and met by a proven
bound (decryption-failures.md, finding 10): FrodoKEM and HQC follow it,
NIST IR 8545 states it, ML-KEM-1024 misses it by 81 bits. CBD(18) at
q = 2^15 is the widest noise that meets it: 2^-266.1 against the weakest
attack's 2^-252.4. CBD(20) would give 2^-217.5 against 2^-255.9.

**Why these choices around it.**
- *One bit per coefficient.* Two bits per coefficient would halve the
  window, and keeping the failure rate would then need half the noise
  variance (CBD(9)): 233.4 / 232.3 instead of 253.9 / 252.4, 20 bits less.
  256 one-bit coefficients keep the window at q/4.
- *q = 2^15 rather than 2^16 or 2^14.* Equal sigma^2 / q gives equal
  security and failures, so q is a free choice: 2^15 packs in 15 bits, and
  its sigma = 3 keeps the secret wide. The research found that the
  dual-hybrid attack, which guesses secret coordinates, beats the primal
  attack by 6-14 bits when the secret's standard deviation is 1.4 or less,
  and loses to it at 2.3-2.8 (attack-cost-estimation.md, item 2a).
  q = 2^14 would need sigma = 2.1.
- *nbar = 32, mbar = 8.* The message needs 32 x 8 coefficients either way.
  The public key grows with nbar and the ciphertext with mbar, and a
  recipient's key is published once while every wrapped file carries a
  ciphertext; so the ciphertext is the small side (15.9 KB, the size of
  FrodoKEM-976's), and encapsulation and decapsulation do a quarter of key
  generation's matrix work.
- *Centred binomial noise.* Exact, sampled with population counts in
  constant time, and its law is known in closed form, so the failure
  computation needs no table. Its width is what the table above chose.
- *No error-correcting code, no ciphertext compression.* Both lower the
  failure rate or the size on paper, and both have broken schemes (LAC's
  failures were 2^48 times likelier than its estimate; compression is the
  one heuristic in ML-KEM's failure analysis). Without them the failure
  law above is exact, not heuristic.

**Security.** Classical and quantum core-SVP (sieving at 2^0.292b and
2^0.265b per BKZ-b call, every polynomial factor left out, which favours the
attacker), and the lattice-estimator (commit 53da598, all its attacks,
through the research's SageMath stand-in, which reproduces the estimator's
own published outputs first):

| | Turing-1026 | ML-KEM-1024 | FrodoKEM-976 | FrodoKEM-1344 |
|---|---|---|---|---|
| Classical core-SVP, primal / dual (one convention) | 253.9 / **252.4** | 255.3 / 253.9 | 206.5 / 205.6 | 271.7 / 270.5 |
| Quantum core-SVP | 228.9 | 230.2 | 186.5 | 245.4 |
| Lattice-estimator, cheapest attack (default model) | **269.7** (primal BDD) | 262.3 (dual-hybrid) | 225.2 (primal BDD) | 281.7 (dual-hybrid) |
| Lattice-estimator, cheaper of primal and dual-hybrid in its core-SVP model | 253.7 | 241.8 | 206.4 | 261.0 |
| Decryption failure | **2^-266.1** | 2^-174.8 | 2^-199.6 | 2^-252.5 |
| Public key / ciphertext (bytes) | 61,592 / 15,934 | 1,568 / 1,568 | 15,632 / 15,744 | 21,520 / 21,632 |

Core-SVP rows use one convention for all four (the GSA model of ADPS16 as
NewHope's scripts run it; FrodoKEM's own tables add log2 b, which puts
Turing-1026 at 261.6 and FrodoKEM-1344 at 279.8). The ciphertext's LWE
instance (n + 32 samples per row of S') is the weaker of Turing-1026's two;
the key's gives 254.2 / 253.0. The estimator treats ML-KEM-1024 as plain LWE,
as every published estimate does. In short: Turing-1026 is at ML-KEM-1024's
level on the plain core-SVP count, ahead of it once hybrid attacks are
counted (ML-KEM's narrow secret loses 8 to 13 bits to the dual-hybrid,
depending on the cost model), behind
FrodoKEM-1344, and has the lowest failure rate of the four. The cost is
size: its public key is 39 times ML-KEM-1024's.

The research's caution applies: core-SVP moves by a bit between published
scripts; the estimator has not been rerun under real SageMath (its stand-in
reproduces all 10 published outputs); and no confirmed polynomial-time
quantum attack on LWE exists as of 2026-09-27
(attack-cost-estimation.md, section 8).

**Failures, exactly.** The failure law is built by convolution (2052
products of CBD(18) samples plus one more), and the union bound over the 256
coefficients needs no independence between them: 2^-274.06 per coefficient,
2^-266.06 per ciphertext. Bombe's `dfr` reproduces FrodoKEM's published rates
(2^-138.7, 2^-199.6, 2^-252.5) to 0.05 bit first, and matches `dfr.py` on
Turing-1026 to 0.05 bit. The figure is an average over keys: twelve random
keys, each computed exactly (`t1026_weak_keys.py`), range from 2^-277.9 to
2^-269.5 (median 2^-275.8); rare heavier keys set the average. The real
code agrees with the law: at two small parameter sets where failures are
common, 3.2 million decrypted bits each, it fails 2.056e-4 of the time
against the law's 2.078e-4 (z = -0.25), and 1.2453e-2 against 1.2480e-2
(z = -0.33).

## The transform

Lattice encryption alone is only secure against passive attackers: with a
decryption oracle, a reused key falls in about 1,200-2,200 queries at
Kyber's sizes (cca-transforms-and-binding.md, finding 1). The
Fujisaki-Okamoto transform makes it secure against chosen ciphertexts by
deriving the encryption's coins from the message and re-encrypting on
decapsulation. Turing-1026's version, ingredient by ingredient:

| Ingredient | What it buys | Source |
|---|---|---|
| FO with implicit rejection (HHK17's U-not-bot) | IND-CCA from IND-CPA and a failure rate delta, in the random-oracle model and (with a square-root loss) the quantum one | Hofheinz, Hövelmanns, Kiltz 2017 |
| A 64-byte salt in the coins and, through c, in both keys | multi-target security: many ciphertexts under one key no longer help a collision search; the salt must enter both keys, or binding breaks as it did for round-4 HQC | salted FrodoKEM; Glabush, Hövelmanns, Stebila (IACR CiC 2026) |
| H(pk) in the coins and in the rejection key | the accepted key depends on the recipient's key, and the rejection key cSHAKE256(z, H(pk), c) gives every MAL binding notion | FO_M, Krämer, Struck, Weishäupl 2025 |
| One 32-byte seed as the secret key | z is derived with everything else, which MAL-BIND-K-PK needs; the decapsulator never accepts an expanded key | Schmieg 2024 |
| Distinct cSHAKE256 labels for G, H, the key and the rejection key | independent random oracles, the oracle cloning the proofs assume | Bellare, Davis, Günther 2020 |
| Failure rate 2^-266 | the delta term of every bound is negligible; no failure-boosting attack reaches it under a 2^64-query limit | decryption-failures.md, section 4 |
| Pair-wise check at key generation | a key corrupted while being made (Rowhammer did this to FrodoKEM) fails at once | FIPS 203 section 7.1 |
| Default-fail selection | the output is the rejection key unless the mask replaces it, so a skipped instruction rejects | pqm4 fault attacks (side-channels note, finding 9) |

No single paper proves this exact combination (salted FO with FO_M
rejection; the research's open question 4). Each piece is proven, the salt
is known not to disturb the binding results, and FO_M changes only a public
input to the rejection hash; so the combination is argued, not proven.
Rejection will be explicit at the file level anyway (a wrong key fails the
file's authentication), which Hövelmanns and Kudinov show is as secure as
implicit rejection in the random-oracle model, up to a rare edge case
(PQCrypto 2025).

## Implementation

- **Constant time.** Secret values are only added, multiplied, masked and
  shifted. `tools/asm_branches.py` now has a `--divs` mode (the KyberSlash
  class): the release build of `lwe` and `turing1026` holds no division
  except three that divide constant allocation sizes by the page size. A
  first version had divisions of public slice lengths from `chunks_exact`;
  the loops now slice by multiplication, so the scan reads zero there. Every
  conditional jump in decryption, sampling, packing and decapsulation tests
  a length, a loop counter, a bounds check or the XOF's position, never a
  decoded bit, a noise value or the comparison. dudect (a leak is
  |t| > 4.5; two full campaign runs): decapsulation of valid against
  tampered ciphertexts |t| 1.3 and 2.2 over 3,000 runs, the re-encryption
  comparison alone, equal against differing, 1.2 and 0.9 over 200,000, key
  generation from fixed against random seeds 1.7 and 3.2 over 600; an
  early-exit comparison put through the same test as the re-encryption
  check is caught at |t| 358 and 416.
- **Memory.** The expanded secret (seed, S, z) and each operation's scratch
  (message, coins, S', the re-encryption) live in locked allocations wiped
  on drop; secret hashing uses a new `xof::SecretXof`, cSHAKE256 written on
  Keccak-f directly, which absorbs and squeezes in parts and wipes its state.
  Bombe's memory scan finds the seed, the noise seed, z, the message, the
  coins, k and the keys only where they belong, after key generation, after
  an encapsulation and two decapsulations, and after drop, even with the
  stack burn turned off. S itself is not searched for: an 8-byte fragment of
  it holds about 14 bits, too few to tell a copy from chance. Key generation,
  encapsulation and decapsulation use at most 3.6, 3.8 and 4.5 KB of stack,
  within the 32 KB burn.
- **Faults.** Every single-bit flip in bits 0-13 of S between expansion and
  the pair-wise check is caught; bit 15 changes an entry by 2^15, which is 0
  mod q, so it changes nothing.
- **Self-test.** `turing::self_test()` now also checks vector 2 of
  `vectors/turing-1026-v1.txt` (public key and ciphertext digests, shared
  key, and the rejection key of a tampered ciphertext); it takes about 60 ms.
- **Speed** here (one core): key generation about 45 ms with its pair-wise
  check, encapsulation and decapsulation about 13 ms each, three quarters of
  it expanding A from cSHAKE256.

## What was run

Section 25 of `bombe attack`, and `tests/turing1026.rs`:

- **Correctness.** The implementation matches an independent reference
  (`refkem1026`: the sha3 library's cSHAKE, A as a full matrix, i64
  arithmetic, bit-by-bit noise and packing, decoding phrased as a range
  test) on public keys, ciphertexts, shared keys and rejection keys, and its
  LWE core matches at four small parameter sets, including ones where a
  sample's bits end mid-byte. It reproduces the four known-answer vectors,
  which the reference generated.
- **Attack cost.** Bombe's core-SVP port reproduces 7 published rows
  (FrodoKEM round 3, NewHope round 2, ADPS16) with their block sizes, and
  perturbed parameters fail the match; then Turing-1026's numbers above.
- **Failures.** FrodoKEM's published rates, Turing-1026's exact rate, and
  the real code's failure counts against the law.
- **The attack itself, at small n.** Bombe's LLL and BKZ run the primal
  attack the estimate prices on keys made by the real key generation, with
  Turing-1026's own q = 2^15 and CBD(18), n cut down:

  | n (lattice dimension 2n + 1) | 20-70 | 80 | 90 | 100 | 1026 |
  |---|---|---|---|---|---|
  | secret recovered by | LLL | BKZ-10 | BKZ-10 or BKZ-16 (one key each) | BKZ-20 (87 s) | BKZ-868 by the estimate |

  The estimate's success condition, fed the root Hermite factors this BKZ
  reaches on random lattices of the same shape (1.0179-1.0182 for BKZ-10,
  1.0167 for BKZ-16, 1.0158 for BKZ-20 at dimension 161), puts the largest
  n each breaks at 89-91, 96 and 100-101. So BKZ-10 breaks 80, sits at its
  limit at 90 (one key fell to it, another needed BKZ-16), and BKZ-16 fails
  at 100, where BKZ-20 succeeds. (LLL does worse than the condition predicts
  for it, n = 88; it already fails at 80. The condition is written for BKZ.)
  The campaign checks every observed break against the condition within 5
  dimensions. So the attack works on the real code, and grows with n as the
  model that prices n = 1026 says.
- **Chosen ciphertexts.** Single-bit changes anywhere in a ciphertext, salt
  included, give the rejection key (the reference's, where compared); the
  right ciphertext under another key gives that key's rejection key; wrong
  lengths are refused.
- **Timing, memory, faults and stack** as above.

## Planted bugs

`tools/mutate.py --round7` plants 20: rejection returning the decrypted
key, a skipped re-encryption check, a check of B' only, a rejection key
without z or without H(pk), coins without the salt or without H(pk), a
shared key that ignores the ciphertext, a pair-wise check that always
passes, a message left unwiped, a noise sampler that skips a bit, decoding
that rounds down, packing that drops a bit, matrix rows that ignore their
index, cSHAKE padded like SHAKE, a failure law with n products instead of
2n, Chen's formula with the wrong exponent, LLL without size reduction,
enumeration trying one sign everywhere, and the reference's decoding window
shifted.

## What is not done

- **One family of assumptions.** A break of LWE breaks Turing-1026. The
  research's advice for robustness against that is a second, non-lattice
  KEM combined with it (hybrid-combiners.md); X-Wing did that with X25519.
  Turing-1026 has no such partner yet.
- **The transform's proof**, for this exact combination (above).
- **The file format** (step 9): Turing-1026 makes the key; the AEAD that
  uses it and the header that carries the ciphertext are still to come.
- **Masking.** Nothing protects decapsulation against power analysis;
  single-trace attacks on lattice code are known (side-channels note,
  finding 7).
- **Multi-ciphertext security of LWE itself** is unsettled in the
  literature (cca-transforms-and-binding.md, finding 6); a stated limit on
  ciphertexts per key belongs in the file format.
- **Speed and size.** Plain LWE is slow and large next to ML-KEM, the price
  of having no ring structure.
