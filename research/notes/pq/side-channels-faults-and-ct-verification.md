# Implementation attacks on lattice KEMs, and how to show an implementation resists them

This note covers attacks on the *implementation* of a lattice KEM (timing, power/EM, faults, compiler-introduced leaks), the countermeasures the literature has measured (constant-time coding, masking, redundancy), and the tools that check constant-time behaviour (dudect, Valgrind secret poisoning, binary-level analysers). It ends with a per-bug-class list of the tests Turing's CI should run and the platform each needs. Date checked: 2026-09-27. Every number and status is in the claim ledger with its source; items marked UNVERIFIED there are open. Scripts are in research/scripts/pq/ (prefix sc_, plus ct_bugclasses.c/.py and build_valgrind_varlat.sh); their outputs are in the local working directory named in each ledger row.

## Key findings

1. **Lattice KEMs have been broken in practice through their implementations, not their mathematics.** KyberSlash (a compiler-emitted `div`), Clangover (a compiler-emitted branch), the FrodoKEM `memcmp` timing attack, single-instruction-skip faults on the FO check, Rowhammer on FrodoKEM key generation and on the FO "fail" flag, and GoFetch (a CPU prefetcher) all recovered keys; several hit the designers' own reference code (Sections 1, 2, 4).
2. **Constant time is a property of the shipped binary, not the source.** Breaking Bad found compiler-introduced secret dependencies in 7.5% (control flow) and 6.4% (memory) of 5,716 library binaries, on every architecture, compiler and optimisation level studied. Reproduced here: clang 21.1.8 still emits the Clangover branch; the June 2024 Kyber fix without its 2026 asm barrier branches under clang 21 at every optimising level; rustc 1.95.0 emits a secret `div` at opt-level z and 0, and turns the textbook Rust mask select `x ^= m & (x ^ y)` into a pointer select plus a load from the chosen address (a secret-dependent memory access) at every optimising level, which an `asm!` barrier or the `cmov` crate avoids (Sections 1.6, 1.8, 5.4).
3. **The standard checkers are blind to KyberSlash.** Valgrind secret-poisoning (ctgrind, TIMECOP) checks branches and addresses only; it stays silent on a secret `div` even when the binary contains one. The KyberSlash authors' Valgrind patch closes this for divisions (and square roots and FP remainders, but not multiplications); it is not upstream (Valgrind HEAD, 2026-09-27) but applies to Valgrind 3.26.0 and builds without root in WSL, and here it flagged exactly the builds that contain a division and nothing else. A dudect timing test on this machine's Zen 3 CPU (2 million measurements, three seeds) did *not* see the KyberSlash divisions at all, although it saw a planted division-timing difference: timing tests speak for one CPU only (Sections 1.8, 5.2, 5.3).
4. **Everything in decapsulation after decryption is secret.** Whether decryption succeeded is exactly what a plaintext-checking oracle needs; the comparison, the hash and PRF of the decrypted message, re-encryption and the final key selection have all leaked it, by timing (GJN 2020, KyberSlash2, Clangover) and by power/EM (Ravi et al. 2020: Kyber512 in 2560 traces; Ueno et al. 2022: 3,072 traces, 7,680 against a masked software PRF). FIPS 203 forbids outputting the reject flag in any form (Sections 1.4, 2.2, 4.1).
5. **Rejection sampling is safe only on public data.** ML-KEM's `SampleNTT` loops on the public seed and FIPS 203 even advises not bounding it (a bound, if used, must be at least 280 iterations; probability of reaching it 2^-261). The same technique seeded from secret data gave key recovery against HQC and BIKE (Section 1.5).
6. **Rust has specific traps.** There is no language- or LLVM-level constant-time guarantee (Rust's own `black_box` documentation says so). `cargo test` runs the dev profile, whose overflow checks put conditional jumps on secret arithmetic and which keeps hardware division; `==` on secret slices calls a variable-time `memcmp`; a hand-written mask select can become a secret-address load. Valgrind client requests work from Rust with a few lines of inline assembly and no crate (Section 5.4).
7. **Power/EM attacks bypass masking when one trace suffices.** Single-trace belief-propagation attacks on the NTT work on masked and constant-time implementations (Primas-Pessl-Mangard 2017; Pessl-Primas 2019; Hamburg et al. 2021); shuffling inside NTT layers is the named countermeasure. The message decoder leaked even when first-order masked (Ngo et al. 2021: masked Saber, 16 traces) (Sections 2.1, 2.3).
8. **Masking is expensive and not a complete defence.** Masked Kyber768 decapsulation costs 3.5x (first order), 50x (second) and 131x (third) the unmasked cycles on a Cortex-M4F; fifth-order masked Kyber was broken with deep learning, and the Roulette fault attack is *helped* by masking. It is warranted only if the threat model includes physical access (Section 3).
9. **The FO check is not a fault countermeasure, and "default fail" is only half a fix.** One skipped instruction (the `cmov` that installs the rejection key) bypassed it in pqm4's Kyber, Saber and NTRU; the literature's fix is a default-fail order, which the pq-crystals reference code now uses. In this note's exhaustive fault simulation of real gcc and rustc binaries, the default-fail order still had 4-6 single skips per build that released K' (all on the 0/1 flag: `call verify`, its `neg`, a loop bound, the `!fail` negation) and dozens that released a byte of K'; one flipped bit of the stored flag also released K', which is the Rowhammer attack of Mondal et al. (ACNS 2024) run from another process. A flag-free order with an independent second check (proposed here, not from a paper) had zero single faults releasing any part of K' in every build. Faults that only need "did the output change?" (Pessl-Prokop) defeat any detect-and-abort scheme; shuffling and control-flow integrity are the literature's answers (Sections 4.1-4.5).
10. **Some leaks sit below any software test.** GoFetch extracted Kyber keys from constant-time code through Apple's data memory-dependent prefetcher (the DIT bit disables it on M3, not M1/M2); Hertzbleed-style frequency effects and speculation are similar. Intel's data-operand-independent-timing list leaves out `DIV` and `IDIV`, and its DOIT mode needs the kernel. These are residual risks to write into Turing's threat model (Section 1.9).
11. **NIST does not require constant time.** FIPS 203 Section 3.3 lists destruction of intermediates, input checks, an approved RBG and no floating point; SP 800-227 Section 3.3 says KEM modules "should" have side-channel countermeasures including constant-time code (Section 1.7).
12. **A concrete CI plan exists and its core is already shown to work here** (Section 6): Valgrind secret-poisoning on release builds; the patched Valgrind for divisions; a `div`/`mul` scan of every shipped target; a compiler-version matrix; dudect on real hardware (as a supplement only); secret wrapper types with compile-fail tests; fault-hook tests and an exhaustive instruction-skip simulation of the decapsulation tail (a ptrace tool written here, works on Rust release binaries). Each row has a negative control that must fail.

## 1. Timing attacks

### 1.1 What "constant time" means here

A program is *constant time* (more precisely: it has *secret-independent* timing) when three things never depend on a secret: which branch is taken, which memory address is read or written, and the operands of any instruction whose running time varies with its operands (division, on some CPUs multiplication). The KyberSlash paper states this three-part rule and calls it "cryptographic constant time" (KyberSlash, TCHES 2025(2), Sec. 7.2, PDF p. 19). The rule is about the *machine code*, not the source: the same C or Rust source can compile to safe or unsafe machine code depending on the compiler, its version, its flags and the target CPU. Every attack in this section is an instance of that gap.

### 1.2 KyberSlash (2023-2025): a division in the source became a `div` in the binary

- **Who and where.** Daniel J. Bernstein, Karthikeyan Bhargavan, Shivam Bhasin, Anupam Chattopadhyay, Tee Kiah Chia, Matthias J. Kannwischer, Franziskus Kiefer, Thales B. Paiva, Prasanna Ravi and Goutam Tamvada. "KyberSlash: Exploiting secret-dependent division timings in Kyber implementations." IACR Transactions on Cryptographic Hardware and Embedded Systems (TCHES) 2025, issue 2, pages 209-234, DOI 10.46586/tches.v2025.i2.209-234; the official page adds "CHES 2025 Best Paper Award". ePrint 2024/1049 (received 2024-06-28, revised 2025-01-15). The saved PDF is byte-identical to kyberslash.cr.yp.to/kyberslash-20250115.pdf.
- **The bug.** The Kyber reference code computed rounding steps as `(x + KYBER_Q/2) / KYBER_Q` with q = 3329. A compiler normally replaces division by a constant with a multiply and shift, which is constant time. But "asking gcc to optimize for code size (-Os) generally disables the conversion of divisions into multiplications" (Sec. 1.1, p. 2), and a footnote adds that on 32-bit MIPS gcc 14.1.0 emits division even when optimising for speed. A hardware divide takes longer for some operands than others, so the running time leaks the value being divided.
- **Two variants.** KyberSlash1 is in `poly_tomsg`, part of decryption: it "directly leaks information about the secret key". KyberSlash2 is in `poly_compress`/`polyvec_compress`, part of encryption: harmless in encapsulation (the ciphertext is public) but, because decapsulation *re-encrypts* (the Fujisaki-Okamoto check), it gives a plaintext-checking oracle and so key recovery (Sec. 1.2, p. 3).
- **Measured attacks (Table 1, p. 3).** KyberSlash1 on Cortex-A7, Kyber512: 1,835,008 decapsulations, 10/10 key recoveries (2 to 4 hours each). KyberSlash2 on Cortex-M4, Kyber768: 24,576 decapsulations, 10/10. KyberSlash2 on Cortex-A55, Kyber768: 36,864,000 decapsulations, 1/1.
- **Worked example (sc_div_by_mul.py).** 1/3329 is close to 80635/2^28 (2^28/3329 = 80635.46), so `(x * 80635) >> 28` divides by 3329.019 instead of 3329. The fixed `poly_tomsg` computes `((2c + 1665) * 80635) >> 28` and keeps the lowest bit; the old code computed `(2c + 1664) / 3329`. For c = 832 both give quotient 0 (bit 0); for c = 833 both give 1 (bit 1); for c = 2497 both give 2 (bit 0): coefficients near q/2 decode to 1, near 0 or q to 0. The shortcut agrees with the division on every coefficient the caller can pass (all 3329 centred and all 3329 canonical values), is wrong on 18,590 of the 65,536 possible 16-bit inputs, and a constant one too large (80636) is caught. So a multiply-shift replacement is only safe with an exhaustive check over the real input range.
- **The fix** replaced each division by an explicit multiply-and-shift: pq-crystals/kyber commit dda29cc (2023-12-01, `poly_tomsg`, "Updated poly_tomsg to prevent a compiler from using DIV") and commit 272125f (2023-12-29, `poly_compress` and `polyvec_compress`, "Removed "/KYBER_Q" ... a DIV instruction could turn into a plaintext-checking oracle"). `ct_bugclasses.c` shows the replacement is exact on every input the callers pass (Section 1.8).
- **Why the usual tools missed it.** "Memcheck does not test for uninitialized divisions; this is why a patch is needed" (Sec. 7.1.1, p. 16). The ctgrind/TIMECOP method checks branches and addresses, not variable-latency instructions. KyberSlash1 was found by formal methods instead: "KyberSlash1 was first discovered by some of the authors of this paper when they were trying to formally verify a Rust implementation of Kyber" (Sec. 7.2, p. 19), by a secret-integer type discipline in which division is simply not defined for secret types (Sec. 7.2.1). Section 5 has what each tool catches.
- **Lesson for Turing.** Two independent guards are needed: (a) a type or lint rule that forbids `/` and `%` on secret values in source, and (b) a binary-level check of the release build for `div`/`idiv` reached by secret data, for every compiler setting that ships.

### 1.3 Clangover (2024): a mask became a branch

- **Source.** Antoon Purnal, proof-of-concept repository github.com/antoonpurnal/clangover (README, fetched 2026-09-27). No peer-reviewed paper was found; the README is the primary source.
- **The bug.** Kyber's `poly_frommsg` turned each message bit into a mask, `mask = -(int16_t)((msg[i] >> j) & 1)`, then `coeff = mask & ((q+1)/2)`. The source has no branch. Clang "has been observed to produce insecure assembly" with a secret-dependent branch for x86, clang v15-18, at `-Os`, `-O1`, `-O2 -fno-vectorize` and `-O3 -fno-vectorize`. The message is secret in decapsulation, so the branch gives a plaintext-checking oracle.
- **Measured attack.** "On an Intel Core i7-13700H (Clang 16.0.6), it takes between 5-10 minutes to leak the entire ML-KEM 512 secret key using end-to-end decapsulation timing measurements." The strategy is a plaintext-checking oracle attack in the style of Ravi et al. and Ueno et al. (Section 2.2).
- **The fix, in two steps.** pq-crystals/kyber commit 0264efa (2024-06-03) moved the selection into a `cmov_int16` function in `verify.c` ("Fixed secret-dependent branch in poly_frommsg introduced by recent versions of clang with some flags"). Commit 7dff53d (2026-07-28, "Add optimization barrier also in cmov_int16") added an empty inline-assembly barrier `__asm__("" : "+r"(b))`, with the comment that it prevents the compiler from "inferring that b is 0/1-valued" and "handling the two cases with a branch", and that it "is not necessary when verify.c and kem.c are separate translation units, but we expect that downstream consumers will copy this code and/or change how it is built". So the first fix relied on the build layout; link-time optimisation or copying the function into one file could undo it. Section 1.8 tests this.
- **Lesson for Turing.** A source-level mask trick is not a guarantee. Rust has the same exposure: LLVM is the same optimiser clang uses. Turing's docs/11 already found this effect in its own code (`gf::mul` masks compiled to 21 conditional jumps). Every secret-dependent select needs an optimisation barrier *and* a binary-level check.

### 1.4 The FrodoKEM comparison attack (Guo, Johansson, Nilsson, CRYPTO 2020)

- **Source.** Qian Guo, Thomas Johansson, Alexander Nilsson. "A key-recovery timing attack on post-quantum primitives using the Fujisaki-Okamoto transformation and its application on FrodoKEM." CRYPTO 2020; ePrint 2020/743.
- **The idea.** An FO-transformed KEM decrypts, re-encrypts and compares the result with the received ciphertext. The comparison handles no key material, so it looked safe to write with `memcmp`. But `memcmp` stops at the first difference. The attacker modifies the *end* of a valid ciphertext by a chosen amount; if decryption still gives the same message, re-encryption reproduces the original ciphertext, which differs from the modified one only at the end, so `memcmp` runs to the end; if the modification caused a decryption failure the difference appears early and `memcmp` returns fast. That timing difference is a decryption-failure oracle, and each answer is a linear inequality on the secret (abstract and Sec. 5, pp. 1-2, 19).
- **Numbers (Sec. 5.3-5.4, pp. 19-20).** FrodoKEM-1344-AES from liboqs on an i5-4200U at 1.6 GHz. The `memcmp` timing difference was "≈4800 reference clock cycles" against "≈12.7M clock cycles" for a whole decapsulation, "less than 0.04%". About 97,000 decapsulations per unknown, 1344 × 8 = 10,752 unknowns, "≈2^30 measured decapsulations" in total, "approximately 136 core-days" of data collection. The abstract gives "about 2^30 decapsulation calls" (exponent confirmed with pdfspans.py).
- **Scope.** The authors say the same flaw (a non-constant-time `memcmp` or short-circuit comparison in the FO check) appeared in the round-2 reference code of LAC, HQC, BIKE, ROLLO and RQC, and in a Java NTRUEncrypt (Sec. 6, p. 21). The fix is a constant-time comparison, which "should not impact the performance of the schemes in any way".
- **Lesson for Turing.** Treat *everything* inside decapsulation as secret, including the comparison and the selection between the real key and the implicit-rejection key. Turing's `checked()` in `crates/turing/src/cipher.rs` already folds the XOR of all bytes before one final test, which is the right pattern; the same must hold for any KEM comparison.

### 1.5 Rejection sampling: fine on public data, fatal on secret data

- **ML-KEM.** `SampleNTT` (FIPS 203, Algorithm 7) draws 12-bit values from an XOF seeded with the public seed ρ and rejects values ≥ q. The number of loop iterations therefore depends only on public data, and the loop may be variable time. FIPS 203 even says implementations "should not bound this loop, if at all possible"; if they do, the limit must not be lower than 280 iterations, whose probability of being reached is 2^-261 (Appendix B, Table 4, PDF p. 55). FIPS 203 also lists the matrix Â as data "easily computed from the public encapsulation key" that "does not require any special protections" (Sec. 3.3, PDF p. 26).
- **Where it goes wrong.** Guo, Hlauschek, Johansson, Lahr, Nilsson, Schröder, "Don't Reject This: Key-Recovery Timing Attacks Due to Rejection-Sampling in HQC and BIKE", TCHES 2022 issue 3, pp. 223-263 (ePrint 2021/1485). In HQC and BIKE the rejection sampler runs inside the deterministic *re-encryption*, seeded from the decrypted message, which is secret. Its timing leaked whether decryption succeeded. HQC key recovery took "approx. 866,000 idealized decapsulation timing oracle queries" at the 128-bit level; for BIKE, "5.8 × 10^7 idealized timing oracle queries" (abstract).
- **How tools see it.** A Valgrind secret-poisoning run that marks all RNG output secret reports the ML-KEM rejection loop as a secret branch; this is a false positive until the seed is declassified. The KyberSlash paper (Sec. 7.1.3, p. 18) notes that SUPERCOP's Kyber768 `compact` implementation passes TIMECOP only because it "has an extra line of code to declassify the rejection condition". `ct_bugclasses.c` reproduces both outcomes (Section 1.8).
- **Lesson for Turing.** Any rejection loop must be classified: seed public (allowed; declassify explicitly in the test harness, with a comment saying why) or seed secret (not allowed; use a fixed-iteration sampler).

### 1.6 Compilers breaking constant time: the systematic evidence

- **Source.** Moritz Schneider, Daniele Lain, Ivan Puddu, Nicolas Dutly, Srdjan Čapkun. "Breaking Bad: How Compilers Break Constant-Time Implementations." ASIA CCS '25, DOI 10.1145/3708821.3733909; arXiv 2410.13489v2 (2 Sep 2025).
- **Study size.** 8 cryptographic libraries, 11 algorithms, 6 architectures (x86-64, x86-i386, armv7, aarch64, RISC-V, MIPS-32), 2 compilers, trace-based dynamic analysis of 44,604 targets (abstract and contributions, pp. 1-2).
- **Result (Sec. 5.1, p. 6).** "In the 5,716 binaries, we found at least one secret-dependent control-flow operation in 429 (7.5%) and at least one secret-dependent memory access in 368 (6.4%)." Issues appeared "in all studied processor architectures, all compilers, and all optimization levels, including the recommended defaults", including in libraries "formally verified to be free of such side channels" (p. 2). Less common architectures (MIPS, RISC-V, x86-i386) were affected more (Sec. 5.2).
- **Mechanism.** "compilers understand certain arithmetic patterns and replace them with secret-dependent branches or memory accesses" (p. 2); "branches to skip expensive computations are a common optimization in both compilers" (Sec. 6.4, p. 10). Their hand-made example: with a boolean that allows a division to be skipped, LLVM on x86-64 inserts a branch that skips the division.
- **Lesson for Turing.** Source review and a source-level proof are not enough. The check has to run on the binary that ships, for each target and each compiler version, and must be re-run whenever the compiler changes. Docs/11 of this project already records this ("It has to be rechecked when the compiler changes").

### 1.7 What the standards require

- FIPS 203 Section 3.3 ("Requirements for ML-KEM Implementations", PDF pp. 25-26) requires destruction of intermediate values, input checking, an approved RBG and no floating point. It does not state a constant-time requirement. It also notes that "ordinary integer division x/y computes ⌊x/y⌋" as the way to realise the rounding in the pseudocode, which is correct arithmetic but exactly the construction KyberSlash exploited when compiled to a hardware divide.
- NIST SP 800-227 (September 2025), Section 3.3 "Additional Requirements" (printed p. 14, PDF p. 22): "Cryptographic modules for KEMs should be designed with appropriate countermeasures against side-channel attacks. This includes protecting against timing attacks with constant-time implementations and protecting memory from leakage." It adds that leaking information about failures and aborts outside the module "should be avoided", and that "Universal guidelines are unlikely to be helpful".

What this shows:

1. **KyberSlash is invisible to the classic tool.** Stock memcheck never reports the division, even in the two builds whose machine code contains `div`. The patched memcheck reports it in exactly those two builds and nowhere else, and never reports the multiply-shift fixes (the negative control). The self-test confirms the fix is exact: 0 mismatches on the 3329 centred inputs and on [0, q) for `tomsg`, 0 of 6657 for `compress` d=4; the shortcut is wrong on 18,590 of the 65,536 possible int16 inputs, so it is correct only because callers reduce first; a deliberately wrong constant (80636) is caught.
2. **clang -O0 also emits the division.** This matters for Rust: `cargo test` builds at opt-level 0 by default. Section 5.4 checks rustc.
3. **Clangover still reproduces with clang 21.1.8**, at exactly the four settings the README lists for clang 15-18, so the compiler behaviour has not gone away in newer versions.
4. **The June 2024 fix alone is fragile.** Without the asm barrier, and with the helper in the same translation unit, clang 21 branches on the secret bit at every optimising level, including the default -O2 and -O3. This is the situation pq-crystals commit 7dff53d (2026-07-28) describes; the barrier removes the branch at every level.
5. **Rejection sampling:** flagged only when its input is marked secret; the declassified (public-seed) run is clean.

### 1.9 Constant-time code is not enough on some CPUs

- **GoFetch.** Boru Chen, Yingchen Wang, Pradyumna Shome, Christopher W. Fletcher, David Kohlbrenner, Riccardo Paccagnella, Daniel Genkin. "GoFetch: Breaking Constant-Time Cryptographic Implementations Using Data Memory-Dependent Prefetchers." 33rd USENIX Security Symposium, 2024. A data memory-dependent prefetcher (DMP) reads memory contents that look like pointers and fetches from them, turning *data* into *addresses*. The authors extract keys from constant-time OpenSSL Diffie-Hellman, Go RSA, CRYSTALS-Kyber and CRYSTALS-Dilithium on Apple m-series CPUs (abstract, p. 2). For Kyber-512 reference code they craft ciphertexts whose decryption contains a pointer only if a guess about a secret coefficient is right, so the DMP gives a decryption-success oracle; "This behavior is not an implementation issue but fundamental to the FO transform" (Sec. 7, p. 13). The Kyber experiment took 59 minutes of data collection, with 392 recoverable coefficients, 8 ciphertexts per coefficient and 32 Prime+Probe samples per ciphertext (Sec. 7, p. 14). Countermeasures (Sec. 8, p. 16): run crypto on efficiency (Icestorm) cores, blinding, or hardware control; footnote 22: "setting the data independent timing (DIT) bit disables the DMP behavior on M3, which is not the case with M1 and M2". The paper also reports DMPs on Intel 13th-generation CPUs and names Intel's DOIT extensions as precedent for turning a DMP off.
- **Intel DOIT.** Intel's "Data Operand Independent Timing ISA Guidance" (web page, "Updated 9/10/2025", read through WebFetch on 2026-09-27; intel.com refused plain curl with HTTP 403, so the page text itself is not saved) says data operand independent timing mode is controlled by `IA32_UARCH_MISC_CTL[DOITM]`, MSR 1B01H bit 0, enumerated by `IA32_ARCH_CAPABILITIES[12]`; it is enumerated on Intel Core processors "based on Ice Lake and later" and Atom "based on Gracemont and later", and older processors behave as if it were enabled. Enabling it "might disable data-dependent prefetching". Only instructions on Intel's separate list are covered (page "Updated 2/23/2026"): that list contains `MUL`, `IMUL`, `MULX`, `CMOVcc`, `SETcc`, `ADC`, `SBB`, the logic and shift instructions, AES-NI, `PCLMULQDQ` and many SIMD instructions, and does **not** contain `DIV` or `IDIV`. So on Intel no mode makes a hardware divide safe on secret data; KyberSlash-style code must be removed, not configured away. Writing the MSR needs ring 0, so a user-space library cannot turn DOITM on by itself.
- **Arm DIT.** A Linux kernel discussion of October 2022 (Ard Biesheuvel's RFC patch "arm64: Enable data independent timing (DIT) in the kernel" and Mark Rutland's reply, LKML) states that Armv8.4 introduced the DIT control, that it lives in PSTATE (so it is saved and restored per thread and user space can set it), that FEAT_DIT is mandatory, and that it resets to 0; at that time the kernel cleared it. Rutland wrote that he knew of "no contemporary implementations where the DIT is both implemented and it being clear results in data-dependent-timing". GoFetch's footnote 22 later showed one: Apple M3, where setting DIT disables the DMP. The exact list of instructions the Arm architecture covers under DIT (in particular whether `SDIV`/`UDIV` are included) is in the Arm Architecture Reference Manual; the Arm web pages that hold it render only with JavaScript and could not be read here (UNVERIFIED). In Rust, the RustCrypto crate `aarch64-dit` (0.1.0, 2024-09-06) wraps enabling and disabling DIT.
- **Lesson for Turing.** Code-level constant time is a contract with the CPU. On Arm, the DIT bit (and on Intel, DOIT mode) is part of that contract; a CI run on x86-64 cannot show that a build is safe on Apple silicon. This is a hardware limit that no software test fully closes; it should be listed as residual risk. Two concrete rules follow from the vendor lists: never divide secret data (Intel excludes `DIV`/`IDIV` from its constant-time list), and on AArch64 set DIT around secret-dependent code (a user-space instruction; `aarch64-dit` in Rust).

## 2. Power and EM attacks

Power and electromagnetic (EM) attacks measure the device while it runs. They matter when an attacker is physically close (a smart card, a microcontroller, a phone in hand) or shares hardware in some other way. They are *not* excluded by constant-time code: constant time hides *when* things happen, not the Hamming weight of the values being processed.

### 2.1 Single-trace attacks on the NTT

- **Primas, Pessl, Mangard, CHES 2017** ("Single-Trace Side-Channel Attacks on Masked Lattice-Based Encryption", LNCS pp. 513-533; ePrint 2017/594). The first single-trace attack on lattice encryption. Three steps: template matching on every modular operation of decryption, *belief propagation* to combine all that partial information across the NTT's butterfly network, then lattice decoding for the key (abstract). Success rate "> 0.9" in a noisy Hamming-weight model "with noise parameters of up to σ = 0.4", and always successful on real EM traces from an ARM Cortex-M4F (Sec. 1, p. 3). Because one trace suffices, *masking does not stop it*: "masking appears to be effective against DPA, yet it does not prevent our attack" (Sec. 7.3, p. 18). The real-device attack exploited timing differences of a `DIV` in modular reduction. Countermeasures named: constant runtime, *shuffling* the butterflies inside each NTT layer (shuffling only the point-wise operations "clearly does not hamper our attack"), random dummy operations (p. 18).
- **Pessl, Primas, Latincrypt 2019** ("More Practical Single-Trace Attacks on the Number Theoretic Transform", LNCS pp. 130-149; ePrint 2019/795). The 2017 attack needed "close to a million multivariate templates" against a variable-time implementation. This one targets *encryption* (recovering the transmitted message, not the long-term key) of an assembly-optimised constant-time Kyber on a Cortex-M4 and needs "only 213 templates" (abstract; checked on a rendering of the page).
- **Hamburg, Hermelink, Primas, Samardjiska, Schamberger, Streit, Strieder, van Vredendaal, TCHES 2021(4):88-113** ("Chosen Ciphertext k-Trace Attacks on Masked CCA2 Secure Kyber"; ePrint 2021/956). Chosen ciphertexts that make the inverse-NTT input sparse, independent of the key, improve noise tolerance. A k-trace attack on the long-term key handles σ ≤ 1.2 in the noisy Hamming-weight model "also for masked implementations"; a 2k-trace variant for Kyber1024 handles σ ≤ 2.2; previous masked-setting attacks worked only up to σ ≤ 0.5 (abstract).
- **Lesson.** Any NTT-based design is exposed to this family. The literature's countermeasures are shuffling inside NTT layers and hiding, not masking alone.

### 2.2 Plaintext-checking oracles from the FO re-encryption

A CCA-secure KEM never tells the attacker whether decryption succeeded. But decapsulation *computes* that fact (it re-encrypts and compares), and a side channel can reveal it. An oracle answering "did this modified ciphertext decrypt to the same message?" is called a *plaintext-checking (PC) oracle*; with it, chosen-ciphertext key-recovery attacks on the underlying CPA scheme work again. Every attack in this subsection builds such an oracle from a different leak.

- **Ravi, Sinha Roy, Chattopadhyay, Bhasin, TCHES 2020(3):307-335** ("Generic Side-channel attacks on CCA-secure lattice-based PKE and KEMs"; ePrint 2019/948). EM leakage from the error-correcting code or from FO operations gives a PC oracle for six round-2 lattice KEMs on pqm4 (Cortex-M4); "complete key-recovery in a matter of minutes on all the targeted schemes" (abstract). Kyber512: "5 · 256 · 2 = 2560 traces", about 99% average success, about 3 repetitions, "about 650 seconds" (Sec. 5.3, p. 18). Their countermeasure: mask the decryption/decapsulation, noted as costly (Sec. 6).
- **Ueno, Xagawa, Tanaka, Ito, Takahashi, Homma, TCHES 2022(1):296-322** ("Curse of Re-encryption: A Generic Power/EM Analysis on Post-Quantum KEMs"; ePrint 2021/849). The leak is in the PRF/PRG used in re-encryption: its trace shows whether its input equals the reference plaintext. Applied to Kyber, Saber, FrodoKEM, NTRU, NTRU Prime, HQC, BIKE (partial) and SIKE (abstract). A deep-learning distinguisher needs no profiling device, because the attacker can profile on the target itself without the key. Traces for key recovery (Table 7, p. 21): Kyber-512 3,072 non-masked / 7,680 with masked software PRF; Kyber-1024 6,144 / 15,360; FrodoKEM-640 51,200 / 128,000; FrodoKEM-1344 86,016 / 215,040. "the first-order masking countermeasures on software are not an essential solution" (Sec. 6.3, p. 20); the attack did not succeed against a threshold-implementation (TI) masked *hardware* AES.
- **Clangover and KyberSlash2** (Section 1) are the timing versions of the same oracle.
- **Lesson.** Every operation after decryption in decapsulation handles data that is secret *because it depends on whether decryption succeeded*: the hash G(m'‖h), the PRF expanding r', re-encryption, the comparison and the final selection. Protecting only the operations that touch the secret key is not enough.

### 2.3 Message encoding and decoding

- **Amiet, Curiger, Leuenberger, Zbinden, PQCrypto 2020** ("Defeating NewHope with a Single Trace", LNCS pp. 189-205; ePrint 2020/368). The message-encoding step, which turns each message bit into a coefficient, leaked the whole shared secret from one power trace of the NIST reference code on a Cortex-M4. With optimisation off "the shared secret can be read from an oscilloscope display directly with the naked eye" (abstract). This is the same function (`poly_frommsg`) whose compiled branch Clangover later exploited by timing.
- **Ngo, Dubrova, Guo, Johansson, TCHES 2021(4):676-707** ("A Side-Channel Attack on a Masked IND-CCA Secure Saber KEM Implementation"; ePrint 2021/079). The decoder leaks even when masked. Against the first-order masked Saber of Van Beirendonck et al. on a Cortex-M4 (STM32F415, compiled with arm-none-eabi-gcc -O3), deep-learning power analysis recovered "both the session key and the long-term secret key from 16 traces" without extracting the random mask (abstract; the conclusion, Sec. 5, PDF p. 20, says this was for LightSaber, and that the profiling and attacked devices can differ); the leakage points are the message decoding `POL2MSG()` and the masked arithmetic shift `poly_A2A()`, the latter "not known before" (Figures 5-6, PDF pp. 10-11). Profiling can be done on the attacked device itself, with no need for a clone with countermeasures off (abstract). Set-up: ChipWhisperer-Lite, CW308T-STM32F4, 24 MHz (PDF p. 9).
- **Lesson.** Bit-to-coefficient encoding (`frommsg`) and the rounding decoder (`tomsg`) are the two hot spots: both process the message one bit at a time, which is the easiest possible leakage target, and first-order masking of the decoder did not remove the leak (Ngo et al.).

## 3. Masking lattice KEMs

**What masking is.** Split each secret x into d+1 random *shares* whose sum (arithmetic masking, mod q) or XOR (Boolean masking) is x. Compute on the shares so that no d intermediate values together reveal anything about x. An attacker must then combine d+1 leakage points, and the number of traces needed grows roughly exponentially in d when the measurement noise is high enough. Linear operations (NTT, additions, multiplication by a public value) are cheap: apply them to each share. Non-linear operations are expensive: the compression/rounding (`tomsg`, `Compress`), the binomial sampler (it needs Boolean shares, but the arithmetic is mod q), the hash functions (SHA-3/SHAKE on shares), and the ciphertext comparison.

### 3.1 Which parts need masking, and what it costs

- **Bos, Gourjon, Renes, Schneider, van Vredendaal, TCHES 2021(4):173-214** ("Masking Kyber: First- and Higher-Order Implementations"; ePrint 2021/483). The first completely masked Kyber, at first and higher order. New pieces: a higher-order masked one-bit compression (a masked bit-sliced binary search), and a way to compare an uncompressed masked polynomial with the compressed public ciphertext, avoiding masked ciphertext compression (abstract). First-order Kyber768 decapsulation: "3.1 million cycles on the Cortex-M4F", "a factor 3.5 overhead" versus unprotected pqm4 (abstract). Table 2 (PDF p. 21, checked on a rendering of the rotated table), Kyber768 decapsulation on STM32F407G, thousands of cycles: unmasked pqm4 882; masked 1st order 3,116; 2nd order 44,347; 3rd order 115,481. The masking cost "is dominated by Keccak operations rather than polynomial arithmetic" (Sec. 4.1, p. 20). First-order masking used 12,072 random bytes per decapsulation (p. 20). The first-order modules were checked with scVerif and a TVLA t-test on 100,000 traces (conclusion, p. 24).
- **Derived slowdowns** (sc_masking_costs.py): on the Cortex-M4F, 3.5× (1st), 50.3× (2nd), 130.9× (3rd order) the unmasked cycles; on the Cortex-M0+, 2.2×, 19.4×, 41.9× against unoptimised C.
- **Heinz, Kannwischer, Land, Pöppelmann, Schwabe, Sprenkels**, "First-Order Masked Kyber on ARM Cortex-M4", ePrint 2022/058. The PDF calls itself a "Report" and the ePrint entry says "Preprint" (revised 2023-12-11). It was not found in Crossref under that title. The task brief called it a TCHES 2022 paper; that could not be confirmed and is treated as wrong until a venue record is found. It reports masked Kyber768 decapsulation in "2 978 441 cycles, including randomness generation", checked by a t-test with 100,000 traces (abstract), and is described as the first liberally licensed open-source masked Kyber for Cortex-M4.

### 3.2 Masking is necessary but not sufficient

- **Masked comparison is easy to get wrong.** Bhasin, D'Anvers, Heinz, Pöppelmann, Van Beirendonck, TCHES 2021(3):334-359 ("Attacking and Defending Masked Polynomial Comparison for Lattice-Based Cryptography"; ePrint 2021/104) broke the masked comparisons of TCHES 2018 and TCHES 2020 with first-order side channels, and the higher-order one of TCHES 2020 with a collision attack needing no side channel at all. They propose a specifically parametrised t-test framework for the re-encryption step that "would have identified the previously mentioned flaws" (abstract).
- **Deep learning against higher-order masking.** Dubrova, Ngo, Gärtner, "Breaking a Fifth-Order Masked Implementation of CRYSTALS-Kyber by Copy-Paste" (ePrint 2022/1713; published at the 10th ACM Asia Public-Key Cryptography Workshop, 2023, pp. 10-20, where Crossref lists a fourth author, Ruize Wang). Neural networks trained by "recursive learning" recover message bits "with the probability above 99%" from ω-order masked Kyber on a Cortex-M4 for ω ≤ 5 (abstract). The masked implementation was their own extension of an earlier first-order one (p. 3).
- **Single-trace attacks bypass masking** (Section 2.1).
- **Lesson for Turing.** Masking is a large engineering project with its own attack literature. It is only worth doing if Turing's threat model includes physical access to the device doing decapsulation. For a desktop or server file-encryption tool, the literature supports constant-time code plus the fault and oracle hygiene below; for embedded or HSM use, a vetted masked implementation is needed and should not be home-made.

## 4. Fault attacks

A fault attack disturbs the computation (clock or voltage glitch, laser, electromagnetic pulse, or Rowhammer bit flips in DRAM) and learns from the wrong or missing output. The FO transform *looks* like a built-in fault countermeasure, since decapsulation re-encrypts and compares, which is "the classic countermeasure of computing the inverse operation" (Pessl and Prokop, abstract). The literature shows it is not enough.

### 4.1 Skipping the FO check

- **Xagawa, Ito, Ueno, Takahashi, Homma, ASIACRYPT 2021** ("Fault-Injection Attacks against NIST's Post-Quantum Cryptography Round 3 KEM Candidates", LNCS pp. 33-61; ePrint 2021/840). In pqm4, "a single instruction-skipping fault in the decapsulation processes leads to skipping the equality test virtually for Kyber, NTRU, Saber, BIKE, and SIKE" (abstract). For Kyber, Saber and NTRU the target is the call to `cmov`, which overwrites the real key with the rejection key on failure. The real key is already in the output buffer before `cmov` is called, so skipping one call returns the real key for an invalid ciphertext and reopens chosen-ciphertext key recovery (Sec. 5.3, p. 11). They also found the FrodoKEM `memcmp` timing leak of Section 1.4 still present in pqm4.
- **Their countermeasures (Sec. 7, p. 19):** *default fail*: initialise the output with the rejection value and overwrite it with the real key only when the check has positively succeeded, so a skipped instruction leaves the rejection value; assembly-level instruction duplication; random delays.
- **FIPS 203 is written the other way round.** In Algorithm 18 (ML-KEM.Decaps_internal, PDF p. 43) the candidate key K' is computed at step 6, the rejection key K̄ at step 7, and K' is overwritten by K̄ only "if c ≠ c'" (steps 9-10). A literal transcription is therefore *not* default-fail. Conformance only requires the same input-output behaviour (FIPS 203 Appendix C preamble), so a default-fail order is allowed. FIPS 203 also states that the reject flag is secret intermediate data that "shall be destroyed" and that "returning the value of the flag as an output in any form is not permitted" (Sec. 6.3, text before Algorithm 18, PDF p. 42).

### 4.2 Faults that only need "did it change?" (effective vs. ineffective)

- **Pessl, Prokop, TCHES 2021(2):37-60** ("Fault Attacks on CCA-secure Lattice KEMs"; ePrint 2021/064). One instruction-skipping fault in the *decoder*. Whether the fault changed the result (effective) or not (ineffective) depends on a secret coefficient's sign; each observation gives a linear inequality in the key. "6,500 faulty decapsulations are required for full key recovery on Kyber512" (simulation), and the attack was demonstrated with clock glitches on a Cortex-M4 (abstract). Crucially: "As our attack only requires distinguishing effective from ineffective faults, various detection-based countermeasures, including many forms of double execution, can be bypassed." Coarse double execution fails because the attacker does not need the faulty key, only whether the fault mattered — "possibly even easier if the device reacts differently upon detecting a fault" (Sec. 7.1, p. 19). Masking the decoder does not stop it (Sec. 4.2). Countermeasures that do work: fine-grained control-flow integrity ("will always detect our attack"), *shuffling* the order in which coefficients are decoded (the attacker no longer knows which index was faulted), fine-grained redundancy for some variants, and protocol-level restrictions (decapsulate only authenticated ciphertexts) (Sec. 7.1, pp. 19-20).
- **Hermelink, Pessl, Pöppelmann, INDOCRYPT 2021** ("Fault-Enabled Chosen-Ciphertext Attacks on Kyber", LNCS pp. 311-334; ePrint 2021/1222). Flip one bit of a valid ciphertext, then fault the decapsulation to "correct" it again; whether decapsulation then succeeds reveals an inequality on the key. "not defeated by many standard countermeasures such as shuffling in time or Boolean masking" (abstract).
- **Delvaux, TCHES 2022(4):637-660** ("Roulette: A Diverse Family of Feasible Fault Attacks on Masked Kyber"; ePrint 2021/1622). Extends the previous attack to more targets (binomial sampling, last INTT layer), bypasses the countermeasure the INDOCRYPT paper proposed, accepts much weaker fault models (set-to-0, random faults, instruction skips), and — the striking point — "masking and blinding methods that randomize intermediate variables kindly help our attack". A "reasonably priced ChipWhisperer board" broke a *masked* Kyber on a Cortex-M4 by clock glitching; solving time went from about 100 minutes to about one minute, tolerating about 25% wrong inequalities (abstract).

### 4.3 Rowhammer: faults from software

- **Fahr, Kippen, Kwong, Dang, Lichtinger, Dachman-Soled, Genkin, Nelson, Perlner, Yerukhimovich, Apon, ACM CCS 2022** ("When Frodo Flips: End-to-End Key Recovery on FrodoKEM via Rowhammer"; ePrint 2022/952). Rowhammer bit flips during FrodoKEM *key generation* produced a public key with larger error, then a decryption-failure attack of "only 200,000 core-hours" recovered the key; KeyGen runs "on the order of 8 milliseconds", so the authors slowed SHAKE with cache flushing to widen the window to 1300 ms (abstract; Sec. 8.2, p. 13). Countermeasures (Sec. 8.2): order the operations so nothing slow sits between sampling S, E and computing B; **recompute key generation and compare the two public keys, aborting on mismatch** — the attacker would need the same flips twice, which the authors call "highly unlikely"; keep E and check it; watch for skewed ciphertext distributions (weak).
- **Mondal, Kundu, Bhattacharya, Karmakar, Verbauwhede, ACNS 2024** ("A Practical Key-Recovery Attack on LWE-Based Key-Encapsulation Mechanism Schemes Using Rowhammer", LNCS pp. 271-300, DOI 10.1007/978-3-031-54776-8_11). This is a *software-reachable* fault on the FO check itself. The target is the "fail" variable that holds the result of comparing the received and re-encrypted ciphertexts; a Rowhammer 1→0 flip makes decapsulation return the real key F(K', H(ct)) for an invalid ciphertext, which is a plaintext-checking oracle (Sec. 4.1, PDF p. 17). The attacker is a co-located process or VM sharing DRAM with the victim, not a person holding the device (Sec. 4.2 and Table 5, PDF p. 18; three Intel desktop CPUs, i7-4770, i7-3770, i5-3330). With their parallel PC oracle, full key recovery needed "57 independent queries to the oracle", i.e. 57 faults on "fail", each "estimated to happen in <350ms with a significantly high probability" (Sec. 4, PDF p. 21). Their improved oracle cuts queries by "as much as 39% for Saber and approximately 23% for Kyber768" (abstract). Masking and shuffling do not help, because the "fail" variable "remains unaffected and unmasked, since it is not dependent on the secret" (Sec. 5.1, PDF pp. 22-23). Countermeasures named (Sec. 5.4, pp. 23-24): fault-resistant masking of Kyber (Berthet et al.'s quasi-linear masking) and DRAM-level Rowhammer defences (PARA, doubled refresh rate, ANVIL, Target Row Refresh, which TRRespass showed insufficient on its own).
- **Lesson from Mondal et al.** A single stored bit that decides "real key or rejection key" is a single point of failure for *remote* fault attackers too, not only for attackers with a glitcher. For Turing this argues for (a) never materialising the decision as one bit in memory: derive the selection mask directly from the full OR-of-XORs difference in registers, then select; (b) a default-fail order, so that the flip that helps the attacker must turn a failure value into a *specific* success value rather than just clearing a bit; (c) an independent second check of the output (Section 4.4). These are design inferences from the attack's mechanism, not measured countermeasures; they need their own fault-simulation test (Section 6, row 8).
- **PQ-Hammer** (Amer, Wang, Kippen, Dang, Genkin, Kwong, Nelson, Yerukhimovich, IEEE S&P 2025, pp. 3567-3582, DOI 10.1109/SP61157.2025.00048) extends Rowhammer key recovery to post-quantum schemes more broadly. Only the bibliographic record was read (Crossref). The accepted manuscript is on the NSF Public Access Repository (par.nsf.gov/servlets/purl/10584474), but that host refused connections from this machine on 2026-09-27 (curl and WebFetch both failed), so its content is UNVERIFIED here.

### 4.4 Comparison with Turing's `encrypt_block_checked`

Turing's block cipher already has a fault countermeasure (`crates/turing/src/cipher.rs`): check a checksum of the round keys, encrypt, decrypt the result and compare with the input without branching on the data, check the round keys again, and on any mismatch wipe the output and return `FaultDetected`. Docs/11 measured that decrypt-and-compare catches 20,000 of 20,000 simulated single faults for differential fault analysis.

What carries over to a lattice KEM, and what does not:

| Turing block-cipher idea | Lattice-KEM analogue | Does the literature say it is enough? |
|---|---|---|
| Decrypt-and-compare, wipe on mismatch | The FO re-encryption check is already this | No. Skipping the check or the `cmov` defeats it (Xagawa et al.); faults whose only observable is "effective or not" defeat any detect-and-abort scheme, and an abort that looks different from a normal result makes them easier (Pessl-Prokop Sec. 7.1). |
| Round-key checksum before and after (persistent faults, Rowhammer) | Checksum or MAC over the stored decapsulation key; recompute key generation and compare public keys | Recomputing KeyGen is the countermeasure Fahr et al. propose (Sec. 8.2). A checksum on dk before and after decapsulation closes the same time-of-check gap Turing closes. |
| Branch-free comparison (`fold` of XORs, then one test) | Constant-time comparison of c and c', constant-time selection of K' vs K̄ | Needed (GJN 2020), and it must be default-fail (Xagawa et al. Sec. 7). |
| Nothing (not needed for a block cipher) | Shuffling the order of coefficient decoding and NTT butterflies | Shuffling is what defeats Pessl-Prokop and helps against single-trace attacks; Hermelink et al. note shuffling in time does not stop their attack. |
| Nothing | Decapsulate only authenticated ciphertexts where the protocol allows | Pessl-Prokop Sec. 7.1: prevents the attack when practical. |

The key difference: a block cipher's DFA needs the *faulty ciphertext*, so wiping it defeats DFA. A KEM's fault attacks mostly need only *one bit* per query (did decapsulation behave normally?), and that bit survives detect-and-wipe. So for a KEM, Turing's pattern is necessary hygiene, not a defence on its own. The implicit-rejection output must look exactly like a normal output (same timing, same code path, no error value), which ML-KEM's implicit rejection is designed to give.

### 4.5 Fault simulation of the key selection on real machine code (this note)

The literature says "use default fail" (Xagawa et al. Sec. 7). Xagawa et al. also point out that the *condition test itself* must be protected at the assembly level, citing [EHiH+14]: "sensitive instruction(s) should be performed only if a condition is surely tested and satisfied" (Sec. 7, PDF p. 19). To see what that means in practice, the last step of decapsulation was compiled and every possible single fault was tried.

**Set-up** (sc_fault_victim.c, sc_fault_victim.rs, sc_fault_sim.c, sc_fault_sim.py). Three versions of "compare c with c', then output K' or K̄", each compiled with gcc 15.2.0 (-O2, -Os, -O0) and rustc 1.95.0 (opt-level 3, s, z, 0):
- *literal*: the order of FIPS 203 Algorithm 18: the output holds K', and is overwritten with K̄ if c ≠ c'.
- *ref*: the order of the pq-crystals reference `crypto_kem_dec` on main (checked 2026-09-27 with the GitHub API): `fail = verify(ct, cmp)`, then the rejection key goes into the output, then `cmov(ss, kr, 32, !fail)`. This *is* the default-fail order.
- *hardened*: a proposal written for this note, not taken from a paper: default fail; no 0/1 flag at all, the select mask is computed straight from the OR of all byte differences; then the difference is recomputed independently (after a compiler barrier, in reverse order) and a second mask reverts the output to K̄ unless that difference is also zero.

A 150-line ptrace program (sc_fault_sim.c; no emulator, no extra software) runs the real Linux binary, stops at the function, single-steps it, and for every dynamic instruction k runs the program once more with instruction k *skipped* (the instruction-skip model of Xagawa et al. and Pessl-Prokop). The input is an invalid ciphertext, so the correct output is K̄. An outcome is "K'" if the real key came out (the FO check was bypassed: a plaintext-checking oracle), "part of K'" if some byte of K' came out (the attacker can still compare it with the byte they expect, so this is also an oracle). For the C builds, a second model flips each of bits 0-31 of each decision variable once (the stored-bit fault of Mondal et al.). Fault-free runs were checked first (invalid → K̄, valid → K'), and the literal order serves as the negative control (it must show a skip that leaks K').

| build | order | dynamic instructions | skips → K' | skips → part of K' | bit flips → K' or part |
|---|---|---|---|---|---|
| gcc -O2 | literal | 541 | 5 | 65 | 2 (fail bit 0 → K'; bit 5 → part) |
| gcc -O2 | ref (default fail) | 542 | 4 | 34 | 1 (fail bit 0) |
| gcc -O2 | hardened | 1235 | **0** | **0** | **0** of 128 |
| gcc -Os | literal | 998 | 6 | 66 | 2 |
| gcc -Os | ref (default fail) | 999 | 6 | 33 | 1 |
| gcc -Os | hardened | 1624 | **0** | **0** | **0** of 128 |
| rustc 3 | literal | 60 | 6 | 9 | not run |
| rustc 3 | ref (default fail) | 62 | 5 | 2 | not run |
| rustc 3 | hardened | 144 | **0** | **0** | not run |
| rustc s | literal / ref / hardened | 699 / 701 / 1421 | 4 / 4 / **0** | 68 / 33 / **0** | not run |
| rustc z | literal / ref / hardened | 799 / 801 / 1686 | 6 / 5 / **0** | 68 / 33 / **0** | not run |

(gcc -O0 and rustc opt-level 0 rows: see the end of this section.)

**What the skips that leak K' are.** In the default-fail (ref) order the `cmov` call is no longer a single point of failure, as Xagawa et al. intended. But the *flag* still is: skipping `call verify`, the `neg` that turns the OR-accumulator into 0/1, a loop-bound compare that ends the comparison loop early, or the `xor ecx,1` / `xor al,1` that computes `!fail`, makes the flag say "equal", and K' comes out. This happened in every gcc and rustc build tested. Skipping the `and` inside the `cmov` loop copies one byte of K' ("part of K'", the 34 and 33 rows). And flipping bit 0 of the stored `fail` value gives K' in both the literal and the default-fail order, which is exactly the Rowhammer fault of Mondal et al. So **default fail, as written in the reference code, fixes the skipped-cmov fault but not faults on the flag.**

**Why the hardened order survived every single fault.** There is no one-bit decision to hit: the mask comes from a multi-bit difference that is non-zero in many bits for any invalid ciphertext, and a fault that corrupts the first mask is undone by the independently recomputed second mask. Defeating it needs two coordinated faults (one in each pass). It costs one more pass over the ciphertext (1,088 bytes for ML-KEM-768), which is small next to re-encryption.

**Limits.** One fault model (single skip) at the binary level, one data-flip model at the C level, x86-64 only, one compiler version each, a 64-byte stand-in for the ciphertext. Multi-fault attacks, faults in the decoder (Pessl-Prokop's effective/ineffective faults) and faults that corrupt the ciphertext comparison inputs are not covered. The hardened order is a proposal with this evidence only; it has not been reviewed in the literature. The simulator itself is the main result for Turing's CI: it runs on any x86-64 Linux ELF, including Rust release binaries (put the functions under test in one `#[link_section]`), in seconds to minutes.

## 5. Constant-time verification methods

### 5.1 Bug classes

Every timing bug above falls into one of these classes. The tools below differ in which classes they can see.

| id | bug class | example in this note |
|---|---|---|
| A | secret-dependent branch written in the source | early-exit `memcmp` in the FO check (GJN 2020) |
| B | secret-dependent branch *introduced by the compiler* | Clangover; `cmov_int16` without barrier (Section 1.8); Turing's own `gf::mul` (docs/11) |
| C | secret-dependent memory address (table lookup, cache) | secret-indexed table; the DMP turns *data* into addresses (GoFetch) |
| D | variable-latency instruction on a secret operand | hardware `div` (KyberSlash); soft-division library call with branches (KyberSlash FAQ); multiply on some CPUs |
| E | library call with data-dependent time | Rust `a == b` on slices lowers to `memcmp`/`bcmp` (Section 5.4) |
| F | secret-dependent loop count | rejection sampling seeded by secret data (Don't Reject This) |
| G | build-profile artefacts | Rust debug builds add overflow-check branches and keep `div` (Section 5.4) |
| H | below the instruction level | DMP (GoFetch), frequency scaling (Hertzbleed), speculative execution |
| I | power/EM value leakage | single-trace NTT attacks; PRF leakage in re-encryption (Section 2) |
| J | faults | FO-check skipping; effective/ineffective faults; Rowhammer (Section 4) |

### 5.2 The tools and what each can see

- **dudect** (Reparaz, Balasch, Verbauwhede, DATE 2017, pp. 1697-1702; ePrint 2016/1123). Measures the running time of two input classes (usually fixed versus random) on the real machine and applies Welch's t-test; "A t value larger than 4.5 provides strong statistical evidence that the distributions are different" (Sec. III, p. 2). Strength: it needs no model of the hardware, so it can see classes C, D and some of H *on the machine it runs on*. Limits stated by the authors: a pass holds only "up to a certain number of measurements" (Sec. IV-e, pp. 5-6); leakage found is "a necessary condition, but not sufficient" for an attack (Sec. IV-f); and results depend on choosing input classes that trigger the slow path (Sec. IV-g). Turing already runs dudect-style tests on eight code paths (docs/13, Sec. 6). In Rust, the `dudect-bencher` crate (0.7.0, 2026-03-23) implements the method.
- **ctgrind / TIMECOP: Valgrind memcheck with secrets marked "undefined".** Langley's 2010 idea: memcheck already tracks, bit by bit, whether each value is initialised and complains when an uninitialised value decides a branch or an address, so marking the secret as uninitialised turns memcheck into a secret-flow checker. Langley stated the assumption explicitly: constant time holds "assuming that the fundamental processor instructions are constant time, but that's true for all sane CPUs" (imperialviolet.org, 1 Apr 2010). TIMECOP applies the method across SUPERCOP and lists the limitation "Valgrind cannot spot cases where variable-time code is caused by variable-time CPU instructions" (post-apocalyptic-crypto.org/timecop). It sees A, B, C, E, F on the paths the test actually executes, in the binary actually tested. It gives false positives when public data derived from a secret-looking buffer is not declassified (Section 1.5). Geimer et al. report that "ctgrind is used by 5 out of the 6 cryptographic libraries performing CT tests" in the survey of Jancar et al. (CCS 2023, Sec. 6.5, p. 9).
- **KyberSlash-patched memcheck** (`--variable-latency-errors=yes`). Adds class D for division instructions: "sdiv or udiv on AArch64, or idiv or div on x86-64", with "preliminary support for catching other variable-latency instructions" (KyberSlash Sec. 7.1.1). The patch is not in upstream Valgrind as of 2026-09-27; this note's build applies it to the 3.26.0 release. Section 1.8 shows it catching the division in exactly the builds that contain one, and it distinguishes secret from public division operands (Section 5.4), which a plain `objdump | grep div` cannot.
- **What exactly the patch checks** (sc_varlat_patch_ops.py, reading the patch text). It adds 41 calls to a new `complainIfVariableLatency` check in Memcheck's instrumenter, covering 39 VEX IR operations: 18 integer divide/modulo forms (`DivU32`, `DivS64`, `DivModU64to32`, `ModU128` and so on), 6 SIMD floating-point divides, 4 x87 floating-point remainders and 11 square roots. **No multiplication** is checked, and the scalar floating-point divides `DivF32`/`DivF64` are not named. So the patch closes the division gap only. Secret-operand multiplication (variable time on some CPUs, per the KyberSlash FAQ's `warning-mul`) still needs the machine-code scan of Section 6 row 3 or a CPU-specific judgement.
- **Binsec/Rel** (Daniel, Bardin, Rezk, IEEE S&P 2020, pp. 1021-1038). Relational symbolic execution on the *binary*: it models two runs with the same public input and different secrets and asks an SMT solver whether branches or addresses can differ. It gives bug-finding and *bounded verification* (a proof for all inputs up to the explored bound). On 338 cryptographic implementations it found that "gcc -O0 and backend passes of clang introduce violations of CT in implementations that were previously deemed secure by a state-of-the-art CT verification tool operating at LLVM level" (abstract). Classes A, B, C, E, F; D is not in its stated policy.
- **ct-verif** (Almeida, Barbosa, Barthe, Dupressoir, Emmi, USENIX Security 2016). Verifies constant time of *optimised LLVM IR*, and can accept benign violations that leak nothing beyond the public outputs (abstract). Because it works before the backend, Binsec/Rel's result above shows it can miss backend-introduced leaks.
- **MicroWalk / Microwalk-CI** (Wichelmann et al., ACSAC 2018; CCS 2022). Dynamic binary instrumentation plus mutual-information analysis that locates and *quantifies* leakage through branches and memory addresses; MicroWalk analysed 15 implementations, "112 million instructions in about 105 minutes of CPU time" (abstract); Microwalk-CI adds JavaScript support and CI integration (abstract).
- **Type discipline** (secret integer types). In HACL*'s F* library, secret integer types have no division, comparison or indexing; a value becomes public only through an audited `declassify` (KyberSlash Sec. 7.2.1). This is what found KyberSlash1. The authors note it "can easily be implemented in any type system that supports abstract types and interfaces, including Rust". Rust crates in this style: `secret_integers` (hacspec, 0.1.7, 2023) and `libcrux-secrets` (Cryspen, 0.0.6, 2026-07-15), whose README adds a Valgrind mode: with `--cfg valgrind_ct_test` and feature `check-secret-independence`, every `classify` marks memory undefined and every `declassify` marks it defined; it also warns that "this does not check for other side channels, such as variable time instructions (e.g., div) or cache side channels".
- **Assembly scanning.** Turing's `tools/asm_branches.py` lists conditional jumps and indexed loads in chosen release functions (docs/11, docs/13). It sees classes B and C statically, for every path, but only by human judgement of which operands are secret. Adding `div`/`idiv` (and on Arm `sdiv`/`udiv`) to its scan is cheap. The KyberSlash FAQ also names `saferewrite`, which "automatically reports warning-div and warning-mul for any secret divisions and secret multiplications detected in machine code" (not tried here).

Geimer et al. (CCS 2023, pp. 1690-1704) compared five tools (Abacus, Binsec/Rel, MicroWalk-CI, dudect, ctgrind) on a common benchmark and found that "existing tools can struggle to find vulnerabilities for a variety of reasons, mainly the lack of support for SIMD instructions, implicit flows, and internal secret generation" (abstract). Their recommendation R3 (Sec. 9.1): tools should handle secrets generated *inside* the code (key generation, PRNG), which none of the 34 surveyed tools explicitly support. For Turing this means key generation needs explicit secret marking of the RNG output in the harness, as the KyberSlash authors did for `test_kyber.c` (Sec. 7.1.2).

### 5.3 The KyberSlash lesson: which tools missed it and why

1. **Source review missed it.** The affected implementations "are carefully designed to be constant-time at the level of source code, by avoiding secret dependent branches and memory accesses" (KyberSlash p. 2).
2. **ctgrind/TIMECOP missed it by design** (Langley's stated assumption; TIMECOP's stated limitation; KyberSlash Sec. 7.1.1). Section 1.8 reproduces this: stock memcheck is silent even when the binary contains `div`.
3. **Testing only the default build missed it.** On x86-64 at gcc -O2/-O3 and clang -O1..-O3 there is no `div` to find (Section 1.8). The division appears only under particular settings: gcc -Os, clang -O0, rustc opt-level 0 and z (Section 5.4), and per the sources gcc 14.1.0 on 32-bit MIPS (KyberSlash footnote 2) and RISC-V at both gcc -Os and -O3 (KyberSlash FAQ). A soft-division library routine (Raspberry Pi 2 build) has input-dependent branches (FAQ).
4. **What found it:** a secret-type discipline during formal verification (KyberSlash1) and manual analysis of submitted code (Bernstein; papers.html history). **What now catches it automatically:** the patched memcheck (Sec. 7.1; Section 1.8 here), and a machine-code scan for secret divisions.
5. **Timing size.** The effect can be one cycle: on AMD Zen 2 "division slows down by a cycle when the numerator reaches 8192"; on SiFive U74 "division speeds up by 62 cycles when the numerator reaches 2048"; the KyberSlash1 demo saw "above 20 cycles" (FAQ). No source reports a dudect test of KyberSlash, so one was run here.
6. **Would dudect have caught it? Not on this machine** (sc_dudect_kyberslash.py; AMD Ryzen 5 5600X, a Zen 3 CPU, under WSL2, gcc 15.2.0). The pre-fix `poly_tomsg` and `poly_compress` (d=4), compiled at gcc -Os so that each contains a hardware divide (confirmed with objdump), were timed with the dudect method: 2,000,000 measurements per run, three seeds, fixed class (all coefficients 0, or all 3300, which puts every `tomsg` numerator above Zen 2's 8192 threshold) against uniformly random coefficients. Result: no run crossed |t| = 4.5 (largest |t| 2.57), and the median cycle count was identical in both classes (4,660 for `tomsg_div`). The controls behaved as they must: the early-exit comparison was flagged in every run (|t| in the thousands), the multiply-shift fixes never were, and a calibration function doing 256 64-bit divisions with small versus full-width dividends was flagged in every run (|t| 7,700 to 12,400; about 250 cycles difference per call, roughly one cycle per division). So the harness does see division timing on this CPU; the Kyber operand range (numerators up to 8,320 for `tomsg`, 54,912 for `compress`) simply does not change this CPU's division time measurably. The same binary is exploitable on Cortex-A7, Cortex-M4 and Cortex-A55 (KyberSlash Table 1) and shows a one-cycle step on Zen 2 (FAQ). **Lesson:** a dudect pass is a statement about one CPU. A timing test on an x86-64 CI runner could not have found KyberSlash; the patched memcheck (which checks the instruction, not the time) does, on any CPU. This is one machine and one compiler; other x86 microarchitectures may differ.

### 5.4 Driving the tools from Rust today (tested)

`research/scripts/pq/sc_rust_ct_probe.rs` transcribes the same bug classes into Rust and issues the Valgrind client requests from Rust itself with `core::arch::asm!`, copying the byte sequence of `VALGRIND_DO_CLIENT_REQUEST_EXPR` for amd64 Linux from valgrind.h (four `rol rdi` by 3, 13, 61, 51, then `xchg rbx, rbx`, with the 6-word argument block in rax and the result in rdx) and the request numbers from memcheck.h (`MAKE_MEM_UNDEFINED` = `VG_USERREQ_TOOL_BASE('M','C') + 1`, `MAKE_MEM_DEFINED` = + 2). No crate is needed. `sc_rust_ct_probe.py` compiles it with rustc 1.95.0 (Windows host, target x86_64-unknown-linux-gnu, no_std staticlib), links it statically with gcc in WSL, and runs each case under stock and patched memcheck. Command: `python research/scripts/pq/sc_rust_ct_probe.py <stock root> <patched prefix> <outdir>`; output in scratch `sc_rust_ct_probe.out` (2026-09-27).

| case | rustc opt-levels where the function contains `div` | stock memcheck flags at | patched memcheck (varlat) flags at |
|---|---|---|---|
| tomsg_div (KyberSlash1 transcription) | 0, z (also 0 with explicit debug-assertions) | 0 (a *branch*: the overflow check on `x + 1664`) | 0 (branch and variable-latency), **z** (variable-latency only) |
| tomsg_mul (fix) | none | none | none |
| frommsg_mask / _blackbox / _asm / _volatile | 0 only (a division of the constants (q+1)/2, public) | none | none (the public division is correctly not reported) |
| eq_slice (`a[..] == b[..]`) | none | every level (branch and address inside glibc `__memcmp_avx2_movbe`, called from `rs_eq_slice`) | every level |
| eq_fold (OR of XORs, one test) | none | none | none |
| rej_secret / rej_public | none | every level / none | every level / none |

What this shows:

1. **Valgrind secret-poisoning works from Rust with no C and no dependencies.** The `crabgrind` crate (0.3.1, 2026-07-20, "Rust bindings to 'Valgrind Client Request' interface") offers the same requests but needs Valgrind's headers at build time (its README: `VALGRIND_INCLUDE`, pkg-config or compiler defaults; without headers "any request will panic at runtime"). `valgrind_request` (1.1.0) was last published in 2016. Crates named `ctgrind` and `timecop` do not exist on crates.io (HTTP 404, 2026-09-27).
2. **rustc also emits a secret `div` at opt-level z**, and only the patched memcheck reports it. Opt-level s did not (rustc 1.95.0, x86-64). So "check the release build" must mean *every* profile that ships, including size-optimised ones.
3. **Rust debug builds are different programs.** Cargo's `dev` profile, which `cargo test` inherits, has `opt-level = 0`, `debug-assertions = true`, `overflow-checks = true` (Cargo book, profiles.md), and rustc turns overflow checks on whenever debug assertions are on, which is the default at opt-level 0 (rustc codegen-options docs, 1.95.0). The overflow check is a conditional jump on the secret sum (`add eax,0x680; cmp eax,ecx; jb <panic>`, read from the opt-level 0 binary), so a constant-time test run under plain `cargo test` reports real branches that the release build does not have, and a clean debug run says nothing about release. Constant-time tests must run on the release profile (and any other shipped profile).
4. **`==` on secret byte slices is not constant time in Rust**: it becomes a libc `memcmp`, which memcheck flags at every opt-level. The fold-then-test pattern (Turing's `checked()`) is clean at every level.
5. **No Clangover-style branch appeared in rustc 1.95.0** for the four `frommsg` variants, at any level. This is one code shape on one compiler version; it does not show rustc is immune (Breaking Bad found such issues across LLVM versions), which is why the check must run on every compiler upgrade.
6. **Rust's own documentation rules out a language-level guarantee.** `core::hint::black_box` "must not be relied upon to control critical program behavior" and "does not offer any guarantees for cryptographic or security purposes"; "there is no mechanism in the entire Rust language that can provide the guarantees required for constant-time cryptography. (There is also no such mechanism in LLVM, so the same is true for every other LLVM-based compiler.)" (library/core/src/hint.rs at 1.95.0, lines 325-334). `subtle` 2.6.1 uses a `read_volatile` barrier by default and describes it as "a best-effort attempt". The RustCrypto `cmov` crate (0.5.4) states it uses conditional-move intrinsics "guaranteed on major platforms ... to execute in constant-time and not be rewritten as branches" (crates.io description); item 8 tests it on x86-64.
7. **LLVM turns a hand-written mask select into a secret-dependent load** (sc_rust_cmov_probe.py, rustc 1.95.0). The textbook branch-free select `x ^= m & (x ^ y)`, with `m` computed from a secret condition, compiles at opt-levels 1, 2, 3, s and z to `test edx,edx; cmove rsi,rdi; mov eax,[rsi]`: the compiler selects between the two *pointers* and then loads through the chosen one, so the load address depends on the secret. Memcheck reports it ("Use of uninitialised value of size 8" in the function) at every one of those levels; opt-level 0 keeps the arithmetic and is clean. Whether this leaks in practice depends on where `x` and `y` live (the same cache line leaks nothing to a cache attacker; different lines or pages can), but it is a secret-dependent memory access that the source did not contain, exactly the effect Breaking Bad measured. Passing the mask through an empty `asm!` block (the idea of pq-crystals commit 7dff53d) removes it at every level (the code becomes `neg; sbb; and; xor`, memcheck clean).
8. **The RustCrypto `cmov` crate behaves as it claims on x86-64 in this test.** Its `cmovnz` for `u32` and `[u8; 32]` compiled to `test` + `cmovne` from its inline assembly at every opt-level, with no conditional jump on the secret, and memcheck reported nothing at any level with the condition marked secret. So memcheck does not treat a hardware `cmov` on a secret condition as an error (no false positive for code built on `cmov`), and the crate's inline assembly survives optimisation. This covers x86-64 only; the crate's AArch64 (`csel`) and portable fallback were not tested (ledger 68).

Other tools from Rust: Binsec/Rel and MicroWalk analyse binaries, so in principle they apply to Rust output; whether they handle Rust binaries (panics, unwinding tables, SIMD) was not checked here (UNVERIFIED). `haybale-pitchfork` (symbolic execution of LLVM IR for constant time) was last published in 2021 (0.4.1).

## What this means for Turing

1. **The implementation, not the lattice problem, is where lattice KEMs have been broken in practice.** Every attack in Sections 1, 2 and 4 recovered keys from implementations of schemes whose mathematics stands: KyberSlash, Clangover, the FrodoKEM `memcmp`, the FO-skip faults, Rowhammer on FrodoKEM, GoFetch. Several hit the *official reference code* written by the designers. Evidence: the sources in Sections 1-4. This supports docs/02's position that the public-key layer should use a vetted implementation.
2. **A home-made "twist" multiplies this attack surface.** Each new non-linear step (a custom rounding, encoding, sampler, error-correcting code or comparison) is a new place for classes A-F, a new PC-oracle source (Section 2.2), a new masking problem (Section 3) and a new fault target (Section 4). Ravi et al. found EM leaks specifically in the error-correcting codes some schemes add (abstract); Pessl-Prokop found that adding an error-correcting code "severely impedes" their fault attack (Sec. 7.1). So the same addition can help against one attack and hurt against another; any twist needs its own implementation-security analysis, not only a cryptanalytic one. This is a risk to flag, not a reason in itself to reject a design.
3. **Design choices that make constant time easier** (evidence in brackets): no division or modulo by q on secrets, or a multiply-shift proven exact on the caller's whole input range (sc_div_by_mul.py, ct_bugclasses self-test); no rejection loop seeded by secrets (Don't Reject This); fixed-length encodings; every select through a barrier-protected constant-time primitive, checked on the binary (Clangover, 7dff53d); a power-of-two modulus removes reductions entirely (FrodoKEM and Saber use one; for a prime q, Barrett or Montgomery reduction is the constant-time route). An NTT is the target of the single-trace attacks in Section 2.1; a scheme without an NTT (e.g. FrodoKEM's plain matrix arithmetic) does not have *that* target, but FrodoKEM had its own timing and Rowhammer attacks (Sections 1.4 and 4.3), so this is not a safety claim.
4. **`encrypt_block_checked` carries over only partly** (Section 4.4). For a KEM: implement decapsulation default-fail (Xagawa et al. Sec. 7), not in the literal order of FIPS 203 Algorithm 18; check a checksum of the decapsulation key before and after (Turing's time-of-check fix); recompute key generation and compare public keys (Fahr et al. Sec. 8.2); make rejection indistinguishable from success in time and code path. None of these defeats effective/ineffective-fault attacks (Pessl-Prokop); shuffling and control-flow integrity are the literature's answers there, at a cost. If Turing's threat model excludes physical access, say so explicitly in the design doc.
5. **Default fail is not enough on its own; the flag is the weak point** (Section 4.5, evidence from this note's simulation, not yet from the literature). In every gcc and rustc build tested, the pq-crystals default-fail order still had 4-6 single instruction skips that output K' (all on the computation of the 0/1 `fail` flag or its negation) and dozens that output a byte of K'; one flipped bit of the stored flag also gives K', which is the Rowhammer attack of Mondal et al. and needs no physical access. A flag-free order (mask straight from the full difference, then an independently recomputed second check) had no single skip and no single bit flip that released any byte of K', in any build tested, for about one extra pass over the ciphertext. This is a concrete, testable option for Turing's decapsulation; it is new here and should be treated as a proposal until reviewed. The same "single decision" observation applies to Turing's own `checked()` (`if diff == 0`): it catches single faults in the cipher, but a data fault plus a skipped check releases a faulty block; that is a two-fault attack, which the literature treats as harder but possible.
6. **Rowhammer puts fault attacks in a desktop threat model.** Mondal et al. flipped the FO "fail" variable from another process on the same DRAM (three Intel desktop CPUs), and Fahr et al. flipped FrodoKEM key generation. A file-encryption tool on a shared machine or VM is in scope for these, unlike glitching attacks, which need the device in hand. The countermeasures that do not depend on DRAM hardware are the ones above: no single stored decision bit, key-generation recompute-and-compare, and checksums over stored keys.
7. **Masking is a separate project.** First-order masked Kyber768 decapsulation costs 3.5× on a Cortex-M4F, second order 50×, third order 131× (Bos et al. Table 2; sc_masking_costs.py), and masked implementations have been broken by deep learning (Dubrova et al., fifth order) and by faults that masking helps (Roulette). For a desktop/server file-encryption tool, constant-time code is the proportionate defence; masking is only warranted if embedded or HSM deployment is planned, and then a vetted masked implementation should be used.
8. **The CI plan of Section 6 closes the gaps this literature shows.** Turing already has dudect, assembly reading, planted bugs and WSL runs. The missing pieces are: a Valgrind secret-poisoning harness run on release builds (row 1), the patched Valgrind for divisions (row 2), a `div`/`mul` scan of every shipped target (row 3), a compiler-version matrix (row 4), secret wrapper types (row 6), and fault-hook tests plus the skip simulator for the KEM path (row 8). Rows 1-4 and 8 ran on this machine for C and Rust samples (Sections 1.8, 4.5 and 5.4), so they are feasible now. Dudect (row 5) stays useful for what it measures, but on this machine it could not have found KyberSlash, so it cannot stand in for rows 2-3.
9. **Use a vetted constant-time select, and check it in the binary.** The obvious Rust mask select was rewritten by LLVM into a secret-dependent load at every optimising level (Section 5.4 item 7); an `asm!` barrier or the `cmov` crate avoided it in this test. Turing's docs/11 already saw the same compiler behaviour in `gf::mul`. Every select on secret data should go through one audited primitive, and row 1 of the CI plan must include it.
10. **Hybrid deployment reduces the stakes but not the need.** With X-Wing, a leak in the ML-KEM half alone does not reveal the combined secret if the combiner is sound and the X25519 half holds (see the hybrid-combiners note); but X25519 falls to a quantum computer, so an ML-KEM implementation leak would still remove the post-quantum protection. Implementation security of the lattice half remains necessary.
11. **Residual risks no software test removes:** data memory-dependent prefetchers (GoFetch), frequency-scaling leaks (Hertzbleed; docs/13 already notes it), speculative execution, power/EM on devices an attacker holds, Rowhammer on DRAM without effective refresh defences, and compiler changes after release. These belong in Turing's written threat model. The vendor controls help only partly: Intel's DOIT list leaves out `DIV`/`IDIV` and DOITM needs the kernel; Arm DIT can be set from user space (Section 1.9).

## Open questions

1. Settled for one machine (ledger 67): dudect on a Zen 3 CPU does not see KyberSlash. Still open: the same test on Zen 2, Intel (several generations) and a Cortex-A class Arm board, to know which CI hardware, if any, would catch it by timing.
2. The KyberSlash Valgrind patch is not upstream. Turing would depend on a patched build that must be re-applied to each Valgrind release (it applied cleanly to 3.26.0). Is there an upstreaming plan (the 20250805 split into an option patch and a division patch suggests one)? Settle by asking the Valgrind project or watching its NEWS.
3. Answered (ledger 69): the patch checks integer divide/modulo, SIMD FP divide, x87 FP remainder and square roots; not multiplication and not scalar DivF32/DivF64. Still open: whether each of these actually fires on x86-64 and aarch64 (only integer division was exercised here).
4. Does the patched memcheck work on riscv64 and on aarch64 Linux runners (ledger 65)?
5. Do Binsec/Rel and MicroWalk run on Rust binaries (ledger 66)? Binsec/Rel would give bounded verification of the release binary, which no test run gives.
6. Venue of Heinz et al. (ledger 54): not found in Crossref or OpenAlex; ePrint lists it as a preprint. Treat as a preprint unless a publisher record appears.
7. PQ-Hammer's findings for lattice KEMs (ledger 63): the manuscript is on par.nsf.gov, which refused connections from this machine; read it when reachable.
8. Intel DOITM is answered from Intel's pages (ledgers 73-74, read through WebFetch; re-check against a saved copy when intel.com allows it). Still open: the list of instructions covered by Arm DIT (ledger 76), and which of Turing's target CPUs change behaviour with DIT set (only Apple M3 is documented, by GoFetch).
9. Fault simulation: answered for single instruction skips on x86-64 Linux with the ptrace tool of Section 4.5. Still open: (a) the same for AArch64 (ptrace single-step works there too, but instruction lengths are fixed at 4 bytes, so the tool needs a small change) and for Cortex-M targets (emulator-based tools); (b) double faults (two skips) against the hardened order; (c) whether the hardened order survives register bit-flip models, which were not simulated at the binary level; (d) review of the hardened order by someone else before Turing relies on it.
10. If Turing adopts a scheme other than ML-KEM (see the pq-families-for-diversity note), its implementation-attack literature must be surveyed separately; this note is ML-KEM/Kyber-centred with FrodoKEM and Saber where attacks exist.
11. The mask-select rewrite (ledger 85) was seen with rustc 1.95.0 on one code shape. Does it occur in Turing's own select code, and with other rustc versions? Settle with row 1 of the CI plan run over Turing's crates (memcheck on release builds) and a scan for `cmov` followed by a load through the selected register.
